# Bidding Service — спецификация сервиса ставок

**Статус:** проектирование, версия 1.1

**Горизонт:** промежуточное решение (3 месяца) с заделом на 12 месяцев

**Связанные документы:** [../Task1/AS-IS.md](../Task1/AS-IS.md), [../Task1/Drivers.md](../Task1/Drivers.md), [../Task1/TO-BE.md](../Task1/TO-BE.md), [../Task1/adr/ADR-001-architecture-evolution-strategy.md](../Task1/adr/ADR-001-architecture-evolution-strategy.md), [interaction.md](interaction.md), [api-gateway.md](api-gateway.md)

**Диаграммы:** [diagrams/C4_Component_Bidding.puml](diagrams/C4_Component_Bidding.puml)

## 1. Назначение

Сервис ставок — bounded context, который отвечает на один вопрос: какую ставку и с каким креативом отдать в аукцион на этот bid request прямо сейчас. Из монолита он выделяется первым: именно он определяет P95 отклика и требует независимого масштабирования (ADR-001, этап 2).

Это core domain. Скорость и точность решения — конкурентное преимущество AdScale, поэтому сервис не покупается и проектируется под собственные правила pacing и ценообразования.

Ответ, пришедший после `tmax` партнёра, в аукционе не участвует. Это потерянная выручка, а не просто медленный ответ, поэтому все архитектурные решения подчинены одному ограничению: P95 ≤ 55 мс и P99 ≤ 70 мс на собственной обработке при SLA партнёра 80 мс.

### 1.1. Целевые показатели

| Показатель | Промежуточное (3 мес) | Финальное (12 мес) |
|---|---|---|
| Входящий поток bid request | 18 000 RPS (15 000 + 20 % от новой DSP) | 50 000 RPS |
| P95 / P99 отклика, весь путь | ≤ 55 / ≤ 70 мс | ≤ 55 / ≤ 70 мс |
| SLA партнёра (жёсткий контракт) | 80 мс | 80 мс |
| Собственная обработка (edge + core) | P99 ≤ 35 мс | P99 ≤ 35 мс |
| Ответ без 5xx | ≥ 99,95 % | ≥ 99,9 % |
| Доступность bid path | 99,95 % | 99,9 % |
| Потеря событий, порождённых сервисом | ≤ 0,01 % | ≤ 0,01 % |
| Перерасход бюджета кампании | ≤ 0,1 % | ≤ 0,1 % |
| Свежесть конфигурации кампаний | ≤ 30 с P95 | ≤ 10 с P95 |
| Реакция kill switch | ≤ 5 с | ≤ 5 с |

Требование «не более 80 мс» из контракта новой DSP строже общего «не более 100 мс», поэтому бюджет строится по худшему из двух.

## 2. Границы сервиса

### 2.1. Что входит в ответственность

| # | Ответственность | Пояснение |
|---|---|---|
| 1 | Приём и валидация bid request | Разбор OpenRTB, обязательные поля, отсев мусора и фрода на уровне схемы |
| 2 | Идентификация контекста | Пользователь, гео, устройство, формат; применение consent-политики |
| 3 | Подбор кандидатов | Кампании и креативы под placement из локального индекса, без БД |
| 4 | Проверка таргетинга | Гео, устройство, язык, site/app, сегменты, brand safety, deals |
| 5 | Учёт бюджета и pacing | Остаток, темп расхода, резерв суммы ставки |
| 6 | Частотные ограничения | Frequency cap по пользователю, устройству, кампании, окну |
| 7 | Расчёт ставки | Модель (CPS/CPM/CPA/vCPM), floor, bid shading, валюта |
| 8 | Выбор победителя | Ранжирование кандидатов, выбор одного или нескольких `imp` |
| 9 | Сборка bid response | `adm`, `nurl`/`burl` с подписью, `crid`, `price`, расширения |
| 10 | Публикация событий решения | `bid.decided`, `bid.no_bid` — асинхронно, вне ответа |
| 11 | Управление политиками ставок | Версионирование и безопасное применение pricing/pacing с откатом |

### 2.2. Что не входит и у кого остаётся

| Не входит | Владелец | Почему граница здесь |
|---|---|---|
| CRUD кампаний, креативов, таргетингов | Campaign Service | Сервис ставок — потребитель конфигурации, а не её автор |
| Хранение и раздача креативов | Campaign Service + Object Storage/CDN | В горячем пути нужен готовый `adm`, ассеты отдаёт CDN |
| Движение денег, ledger, сверка | Billing Service | Финансовая целостность требует ACID и отдельного владельца |
| Агрегация показов/кликов, отчётность | Statistics / Reporting | Считается по событиям, не в ответе |
| Построение сегментов и профилей (DMP) | Targeting / Profile Service | Другой профиль данных и частота изменений |
| TLS, аутентификация партнёров, квоты, DDoS | API Gateway | Сетевой слой, не бизнес-логика; см. [api-gateway.md](api-gateway.md) |
| Онбординг партнёра, контракты, отчётность для DSP | DSP Adapter Service | Антикоррупционный слой и юридическая граница |
| Кабинет рекламодателя (UI и BFF) | Cabinet BFF | Вне критического пути |

Границу можно сформулировать так: сервис владеет решением и его состоянием во время аукциона. Конфигурацию он читает, деньги резервирует и делегирует, следствия показа публикует. Если компонент не влияет на ответ в пределах 55 мс, в сервис ставок он не входит.

### 2.3. Две единицы развёртывания

Границы контекста и границы развёртывания здесь не совпадают: внутри одного bounded context две единицы.

| Единица | Роль | Технология | Почему отдельно |
|---|---|---|---|
| **Bid Edge** | Протокольный адаптер: OpenRTB → внутренняя модель, валидация, сборка ответа, публикация событий | Go | Плотный I/O, частые изменения формата, изоляция «грязного» внешнего протокола |
| **Auction Core** | Движок: индекс, фильтрация, ранжирование, ценообразование, pacing | C++ (переиспользуется существующий код) | Требование не перерабатывать ядро; CPU-bound, чувствителен к GC и кэш-промахам |

Между ними один синхронный переход с бюджетом ≤ 2 мс P99 (gRPC, HTTP/2, та же AZ). Взамен получаем независимое масштабирование и релизный цикл; платим одним хопом, который укладывается в бюджет с запасом.

### 2.4. Context map

| Отношение | Тип | Направление | Характер |
|---|---|---|---|
| DSP → AdScale | Conformist + ACL | входящее | Протокол диктует партнёр; ACL на gateway/edge |
| Bidding → Campaign | Customer/Supplier | исходящее (чтение) | Конфигурация приходит событиями + snapshot pull |
| Bidding → Targeting | Customer/Supplier | исходящее (sync) | Опциональная зависимость, деградирует без отказа |
| Bidding → Billing | Customer/Supplier | исходящее (async) | Ставка резервирует, списание делает Billing по impression |
| Bidding → Statistics | Published Language | исходящее (async) | Событие — публичный контракт, потребители независимы |
| API Gateway → Bidding | ACL | входящее | Единая внутренняя модель после трансляции |

## 3. API

Контуров три, и требования у них разные: внешний диктует партнёр, внутренний горячий диктуем мы, административный редкий, но самый опасный.

### 3.1. Внешний контракт (OpenRTB 2.6 через API Gateway)

| Метод | Путь | Назначение | Примечание |
|---|---|---|---|
| `POST` | `/rtb/v2/bid` | Аукцион | OpenRTB 2.6, `application/json`, HTTPS |
| `POST` | `/rtb/v3/bid` | Задел под OpenRTB 3.0 | Не включается до подтверждения партнёра |
| `GET` | `/rtb/v2/health` | Health/readiness для партнёра | mTLS, без квоты |
| `POST` | `/beacon/imp`, `/beacon/clk` | Учёт показа и клика | Обрабатывает Event Collector, не bidding |

Сервис ставок не терминирует TLS и не проверяет API-ключи — это делает gateway. Внутрь приходит аутентифицированный запрос с заголовками `X-Partner-Id`, `X-Request-Id`, `X-Deadline-Ms` и доверенным идентификатором соединения.

#### 3.1.1. Семантика ответов

| Ситуация | HTTP | Тело | Что видит DSP |
|---|---|---|---|
| Есть ставка | `200` | BidResponse | Участвует в аукционе |
| Нет подходящей кампании | `204` | — | Штатный no-bid, не ошибка |
| Перегрузка, breaker открыт, дедлайн исчерпан | `204` + `X-No-Bid-Reason` | — | Быстрый no-bid вместо тайм-аута |
| Невалидный запрос | `400` | `{"error":...}` | Ошибка интеграции |
| Нет/просрочен ключ, mTLS | `401`/`403` | — | Ошибка аутентификации |
| Превышена квота | `204` | — | No-bid, не 429: 429 партнёр считает ошибкой |
| Внутренняя ошибка до аукциона | `500` | — | Инцидент, цель ≤ 0,01 % |

`5xx` здесь считается багом, а не режимом деградации. Перегрузка и отказы выражаются через `204` в пределах 5 мс: это защищает метрики партнёра и не провоцирует повторные запросы, которые только усилят перегрузку.

Заголовки ответа: `X-Request-Id` (= trace id), `X-Config-Version`, `X-No-Bid-Reason`, `X-Response-Time-Ms`, `Server-Timing` — последний нужен для разбора SLA-споров.

#### 3.1.2. Обработка `tmax`

1. `tmax` переводится в абсолютный дедлайн: `deadline = now + min(tmax, бюджет партнёра)`.
2. Бюджет партнёра — конфигурация gateway (80 мс для новой DSP, 100 мс для остальных).
3. Дедлайн передаётся в gRPC как deadline и как поле `deadline_epoch_ms` для C++ ядра.
4. Если до дедлайна < 15 мс — немедленный `204` без новых дорогих операций.

### 3.2. Внутренний контракт Bid Edge → Auction Core

gRPC, `proto3`, пакет `adscale.bidding.v1`. Контракт — чистая функция от (контекст, конфигурация, счётчики): побочных эффектов нет, повтор с тем же `auction_id` не приводит к двойному расходу.

| Сообщение | Ключевые поля |
|---|---|
| `DecideRequest` | `auction_id`, `partner_id`, `placement_key`, `imps[]`, контексты (user/device/geo/consent), `deadline_epoch_ms`, `max_candidates`, `shadow` |
| `Impression` | `imp_id`, формат, размеры, `bidfloor_micros`, валюта, `deal_ids`, `secure` |
| `DecideResponse` | `outcome` (BID / NO_BID), `seatbid[]`, `no_bid_reason`, `config_version`, `degraded`, `degrade_reason` |
| `Bid` | `imp_id`, `campaign_id`, `creative_id`, `price_micros`, валюта, `adm`, `nurl`, `burl`, `cat`, `crid`, `deal_id` |
| `Health` | `serving`, `config_version`, `degraded` |

Несколько договорённостей. `price` — целое в micro-USD, деньги никогда не передаются как `float`. `auction_id` — ULID: сортируемый, генерируется на edge, служит ключом корреляции и идемпотентности. Совместимость держим только backward-compatible изменениями.

### 3.3. Административный API

Контур редкий, но финансово опасный: ошибка в pricing-политике стоит денег за минуты.

| Метод | Путь | Назначение | Защита |
|---|---|---|---|
| `POST` | `/admin/v1/config-releases` | Создать черновик релиза | OIDC + RBAC, 4 глаза |
| `POST` | `/admin/v1/config-releases/{id}:activate` | Активировать | Идемпотентно, аудит, автооткат при росте CPL |
| `POST` | `/admin/v1/config-releases/{id}:rollback` | Откат | ≤ 5 с |
| `POST` | `/admin/v1/kill-switch` | Мгновенный стоп (партнёр/кампания/глобально) | Приоритетный канал, ≤ 5 с |
| `GET` | `/admin/v1/state` | Версия конфигурации, лаг снапшота, состояние breaker'ов | Read-only |
| `POST` | `/admin/v1/drain` | Вывод пода из балансировки | Graceful shutdown |

Kill switch не идёт через Kafka. У него отдельный приоритетный путь (pub/sub и локальный TTL 5 с), потому что остановка показа при фроде не должна зависеть от лага шины.

### 3.4. Потребляемый контракт конфигурации

| Источник | Что | Как | Гарантия |
|---|---|---|---|
| Campaign Service | Полный снапшот кампаний | `GET /internal/v1/snapshots/{version}` (REST, ETag) | Точка отсчёта при старте и при отставании |
| Campaign Service | Дельта-изменения | Kafka `campaign.changed.v1`, ключ `campaign_id` | At-least-once, применение по версии |
| Targeting | Сегменты пользователя | gRPC `Targeting.Lookup`, дедлайн 5 мс | Опционально: без сегментов решение принимается |
| Billing | Состояние бюджета (сверка) | Периодическая сверка, `GET /internal/v1/accounts/{id}/budget` | Не в горячем пути |

## 4. Модель данных

### 4.1. Принципы

1. Три класса данных: конфигурация версионируется и воспроизводима, счётчики приблизительны и восстанавливаемы, аудит неизменяем.
2. В горячем пути нет чтений из БД. Данные решения живут в памяти пода или в Redis; PostgreSQL нужен для конфигурации, аудита и восстановления.
3. Деньги хранятся целыми числами: все суммы в micro-USD (`bigint`), доли — в базисных пунктах.
4. На dataset один писатель: сервис пишет только `bidding.*` и свои топики.
5. Кеш не является источником истины. Redis можно потерять целиком — состояние пересчитывается из ledger и снапшота.

### 4.2. PostgreSQL: схема `bidding`

Собственный инстанс, отдельный от монолита. На старте primary и синхронная реплика, позже read replica для админ-чтений.

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `config_release` | Версия набора политик (атомарное применение и откат) | `id`, `version`, `status`, `checksum`, `author`, `activated_at` |
| `pricing_policy` | Модель ценообразования | `scope_type`, `scope_id`, `model`, `base_bid_micros`, `floor_micros`, `shading_bp`, `config_release_id` |
| `pacing_policy` | Темп расхода | `campaign_id`, `mode`, `daily_budget_micros`, `hourly_curve_bp`, `timezone` |
| `frequency_cap` | Частотные ограничения | `campaign_id`, `scope`, `max_count`, `window_seconds` |
| `campaign_snapshot` | Read model кампаний (перестраиваемая) | `campaign_id PK`, `version`, `etag`, `campaign_json`, `targeting_json`, `source_offset` |
| `outbox` | Надёжная публикация событий | `aggregate_id`, `event_type`, `payload`, `published_at` |
| `audit_log` | Аудит политик и kill switch | `actor`, `action`, `object`, `before`, `after`, `trace_id` |

Инварианты: `config_release` применяется транзакционно, то есть либо все политики активны, либо ни одной; `campaign_snapshot.version` монотонна, событие с `version <= applied_version` игнорируется; `audit_log` — append-only с retention 12 месяцев.

PostgreSQL выбран потому, что при смене релиза нужны транзакции, а ещё нужны аудит и восстановление после потери кеша. Объём — десятки тысяч кампаний, нагрузка записи — единицы операций в секунду.

### 4.3. Redis: горячее состояние

Redis Cluster, 6 шардов плюс реплики, `maxmemory-policy noeviction`: потеря счётчиков допустима, внезапное вытеснение — нет.

| Ключ | Содержимое | TTL |
|---|---|---|
| `bid:camp:{campaign_id}` | `spent_micros`, `reserved_micros`, `pacing_tokens`, `version` | 48 ч |
| `bid:pace:{campaign_id}:{minute}` | счётчик показов за минуту | 2 ч |
| `bid:cap:{campaign_id}:{scope}:{key}:{window}` | счётчик частоты | окно + 10 % |
| `bid:kill:{scope}` | флаг остановки | 5 с |

Проверка и резервирование выполняются одним Lua-скриптом на ключах с общим hash tag, так что гонок между подами нет. Резерв живёт 30 с и идемпотентен по `auction_id`. Если Redis потерян, включается режим локальных счётчиков (`LOCAL_PACE`) на долю трафика не более 10 %, а восстановление идёт из ledger Billing. `KEYS` и `SCAN` в горячем пути не используются.

### 4.4. In-memory индекс пода

| Структура | Содержимое | Размер (оценка) |
|---|---|---|
| `byPlacement` | `placement_key → []CampaignRef` | 60–120 тыс. записей |
| `byCampaign` | `campaign_id → *CampaignConfig` | ~200 МБ |
| `creativeIndex` | `creative_id → prepared adm` | ~300 МБ |
| `geoIndex` / `segmentIndex` | Обратные индексы для отсева | ~50 МБ |

Индекс живёт в двух генерациях, указатель подменяется атомарно — блокировок на чтение при 18 000 RPS быть не должно. В горячем пути не аллоцируем: арены в C++, `sync.Pool` в Go. Версия конфигурации видна в ответе (`X-Config-Version`), снапшот одинаков на всех подах и проверяется по checksum, поэтому решения воспроизводимы.

### 4.5. Kafka: события

| Топик | Направление | Ключ | Партиции | Retention | Семантика |
|---|---|---|---|---|---|
| `adscale.bidding.bid.decided.v1` | produce | `auction_id` | 64 | 24 ч | At-least-once, компактная схема |
| `adscale.bidding.bid.no_bid.v1` | produce (sampled 10 %) | `campaign_id` | 16 | 12 ч | Диагностика, не деньги |
| `adscale.campaign.changed.v1` | consume | `campaign_id` | 32 | `compact` | Применение по монотонной версии |
| `adscale.campaign.snapshot.ready.v1` | consume | `version` | 4 | 7 дней | Триггер догрузки снапшота |

Схемы в Avro, Schema Registry, режим `BACKWARD_TRANSITIVE`. PII минимизирована: `user_id` передаётся только хешем, raw IP не публикуется, consent-флаги обязательны.

Событие расхода (`spend`) сервис не публикует — его формирует Billing по `impression`. Bidding публикует только решение и диагностику, то есть следствия аукциона, а не деньги. Партиционирование по `campaign_id` даёт горячие партиции у крупных кампаний, но потребителям порядок не нужен: операции аддитивны и дедуплицируются по ключу. Это вопрос пропускной способности, а не корректности.

### 4.6. Чего в модели данных нет

Показов и кликов (Statistics/ClickHouse), баланса и ledger (Billing), кампаний как источника истины (Campaign Service, здесь только перестраиваемая read model), полного хранилища bid request/response. Последнее не хранится из-за PII и объёма 1,5 млрд в сутки: остаётся выборка 0,1 % плюс все ошибки.

## 5. Бюджет задержки

Бюджет строится сверху вниз от контракта 80 мс. У каждого этапа есть владелец и алерт на выход за границы.

| Этап | Бюджет P95, мс | Кто владеет | Комментарий |
|---|---|---|---|
| Сеть партнёр → edge | 5 | Сеть/GSLB | Вне нашего контроля, измеряется пассивно |
| API Gateway (TLS, auth, лимиты, breaker) | 3 | Gateway | Собственная задержка ≤ 2 мс P99 |
| Bid Edge: разбор, валидация, идентификация | 7 | Bidding | OpenRTB 2–3 КБ, потоковый разбор |
| Targeting (параллельно, опционально) | 5 | Targeting | Дедлайн 5 мс, иначе без сегментов |
| Auction Core: индекс, фильтр, ранжирование | 20 | Bidding | Доминирующая часть — CPU |
| Pacing и frequency cap (Redis, ≤ 2 RTT) | 4 | Bidding | Пайплайн, hash tag на шард |
| Сборка ответа и сериализация | 5 | Bidding | Предсобранный `adm` |
| Egress → партнёр | 6 | Сеть | — |
| **Итого P95** | **55** | | Резерв 25 мс до 80 мс |
| **Цель P99** | **70** | | Резерв 10 мс до контракта |

Дедлайн едет через все хопы, и ни один компонент не может занять чужой бюджет. За 15 мс до дедлайна срабатывает guard. Синхронных переходов не больше трёх (gateway → edge → core), targeting идёт параллельно. Релиз блокируется, если P95 вырос больше чем на 3 мс. Оптимизации нацелены на P99.9: именно хвост превращается в просроченные ответы.

## 6. Масштабирование и эксплуатация

### 6.1. Ёмкость

| Параметр | Значение | Обоснование |
|---|---|---|
| Пропускная способность пода (edge) | 2 000 RPS при P99 ≤ 35 мс | 4 vCPU, 2 ГБ, TLS не терминируется на поде |
| Пропускная способность пода (core) | 2 500 RPS при P99 ≤ 20 мс | 4 vCPU, 4 ГБ, весь индекс в памяти |
| Промежуточное решение | 12 edge + 10 core (N+2 в каждой из 3 AZ) | 24 000 RPS при цели 18 000 |
| Финальное решение | 26 edge + 22 core | 52 000 RPS при цели 50 000 |
| Сеть | 25 Гбит/с на узел | 18 000 × ~3 КБ запрос + ~2 КБ ответ ≈ 90 МБ/с |

Масштабирование горизонтальное, поды stateless: в поде нет ничего, что нельзя восстановить. HPA смотрит на RPS и на P95 собственной обработки. Второй сигнал важнее: он реагирует на деградацию, а не на нагрузку.

### 6.2. Развёртывание

- Контейнер, Kubernetes, три AZ, `topologySpreadConstraints`, anti-affinity.
- Канареечный релиз 1 % → 5 % → 25 % → 100 %, автооткат при P99 выше 35 мс или росте технического no-bid выше 0,5 %.
- Graceful drain: под перестаёт принимать соединения и завершает in-flight запросы (≤ 2 с).
- Shadow/dual-run для новой DSP: первые сутки идут в теневом режиме без резерва бюджета, расхождение цены больше 5 % блокирует выкатку.
- Feature flags на pricing-модель, набор кандидатов и порядок ранжирования.

### 6.3. Наблюдаемость

| Сигнал | Метрика | Алерт |
|---|---|---|
| Задержка | `bid_decision_duration_seconds{stage,partner}` | P99 core > 25 мс 5 мин |
| Просрочки | `bid_deadline_exceeded_total{partner}` | > 0,1 % за 5 мин |
| No-bid | `bid_no_bid_total{reason}` | Рост технических причин > 0,5 % |
| Деградация | `bid_degraded_total{reason}` | Любое значение > 0 за 1 мин |
| Бюджет | `bid_budget_overspend_ratio` | > 0,05 % |
| Ёмкость | `bid_inflight_requests` | > 80 % лимита |

Сквозная трассировка: `auction_id` = trace id, W3C `traceparent` от gateway. Сэмплирование tail-based: 100 % ошибок и запросов дольше 60 мс, 1 % успешных.

## 7. Деградация

Полные паттерны описаны в [interaction.md](interaction.md#7-паттерны-надёжности). Здесь только то, что важно для границ сервиса.

| Отказ | Поведение сервиса ставок | Влияние на выручку |
|---|---|---|
| Targeting недоступен | Ставка без сегментов, флаг `degraded` | Падение CTR, выдача продолжается |
| Redis недоступен | Локальные счётчики pacing, консервативные ставки, ≤ 10 % трафика | Недобор без перерасхода |
| Kafka недоступна | События буферизуются локально; сначала теряется телеметрия, деньги — только через outbox | Нет потери денег |
| Снапшот устарел | Работа по последнему снапшоту (TTL 15 мин), затем дефолтные политики | Ограниченный недобор |
| Auction Core деградировал | `204` за 5 мс, breaker на edge | Потеря аукционов вместо тайм-аутов |
| Полный отказ сервиса | Gateway отдаёт `204` из кеша дефолтных ставок или пустой ответ | Управляемая потеря, SLA не страдает |

Общий принцип простой: лучше быстрый no-bid, чем опоздавшая ставка, и лучше консервативная ставка, чем перерасход.

## 8. Открытые вопросы

| # | Вопрос | Влияние | Как закрываем |
|---|---|---|---|
| 1 | Версия OpenRTB и `tmax` новой DSP | Бюджет задержки, набор полей | Подтвердить на онбординге, контрактный тест |
| 2 | Аукцион первой или второй цены | Модель ставки, bid shading | Поддержать оба режима флагом |
| 3 | Consent-модель (GDPR/GPP) | Персонализация, идентификаторы | Юридическое подтверждение, поля обязательны в схеме |
| 4 | Мульти-imp запросы | Кратность нагрузки на ядро | Ограничение 8 `imp`, замерить |
| 5 | Видео и native-форматы | Другой `adm`, другой бюджет | Отдельные обработчики, ядро не меняется |
| 6 | Требования к brand safety и `bcat`/`badv` | Дополнительные фильтры | Правило в ядре, конфигурируемое |
| 7 | Необходимость `ads.cert`/`schain` | Доверие цепочки поставки | Включить в контракт edge, не блокирует MVP |
