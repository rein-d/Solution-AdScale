# Схема взаимодействия AdScale

**Статус:** проектирование, версия 1.1

**Связанные документы:** [../Task1/TO-BE.md](../Task1/TO-BE.md), [../Task1/Drivers.md](../Task1/Drivers.md), [bidding-service.md](bidding-service.md), [api-gateway.md](api-gateway.md)

**Диаграммы:** [diagrams/](diagrams/)

## 1. Задача

Нужно решить, как компоненты AdScale общаются между собой и с внешним миром: какой протокол, синхронно или асинхронно, с какими гарантиями и что происходит при отказе. Отсюда пять вопросов:

1. REST, gRPC или асинхронный обмен — для внутренних вызовов?
2. Какой протокол для интеграции с DSP?
3. Почему Kafka для событий кликов и показов?
4. Почему gRPC для Bidding, но REST для Campaign?
5. Нужен ли API Gateway и какой?

Ограничения взяты из [../Task1/Drivers.md](../Task1/Drivers.md): критический путь ≤ 55 мс P95 при контракте партнёра 80 мс, 18 000 RPS на промежуточном этапе и 50 000 RPS в финале, потеря событий ≤ 0,01 %, списания идемпотентны. Инфраструктуры (Kubernetes, mesh, Kafka) на старте нет, команда ограничена, срок — три месяца.

## 3. Выбор протоколов для внутренних взаимодействий

### 3.1. Критерии

| Критерий | Вес | Почему важен в AdScale |
|---|---|---|
| Задержка и накладные расходы | высокий | 55 мс бюджета, три синхронных хопа максимум |
| Стоимость CPU на сериализацию | высокий | 18 000 RPS × 3 КБ × 3 хопа |
| Строгость контракта и эволюция | высокий | 6 команд, контрактные тесты обязательны |
| Дедлайны и отмена | высокий | Опоздавший ответ бесполезен |
| Поддержка в Go и C++ | средний | Edge на Go, ядро на C++ |
| Отлаживаемость и порог входа | средний | Команда без выделенного SRE |
| Совместимость с браузером и партнёрами | низкий для bid path | Кабинет — отдельный контур |

### 3.2. Сравнение

| Свойство | REST/JSON (HTTP/1.1) | REST/JSON (HTTP/2) | gRPC (protobuf) | Асинхронный (Kafka) |
|---|---|---|---|---|
| Формат | текст | текст + gzip | бинарный | бинарный, batched |
| Накладные расходы на хоп | 1–3 мс | 0,5–1,5 мс | 0,2–0,6 мс | доставка 5–100 мс |
| Контракт | OpenAPI, необязательный | OpenAPI | `.proto`, обязательный | Avro + Schema Registry |
| Дедлайн/отмена | вручную | вручную | встроено | нет понятия |
| Обратное давление | нет | flow control | flow control + лимиты | лаг консьюмера |
| Браузер | да | да | только gRPC-Web | нет |
| Отладка | `curl`, любой прокси | так же | `grpcurl` | Kafka UI, lag-метрики |
| Зрелость в команде | высокая | высокая | средняя | средняя |

### 3.3. Решение по контурам

Bidding Service работает на gRPC.

1. Бюджет задержки. На 18 000 RPS разница между JSON и protobuf — единицы миллисекунд на каждом из трёх хопов. При P95 55 мс это 5–10 % бюджета, которые нечем компенсировать.
2. Дедлайны — часть контракта. `tmax` партнёра превращается в gRPC deadline, который отменяет работу в ядре и освобождает CPU. С REST отмену пришлось бы реализовывать вручную, и до C++ ядра она бы не дошла.
3. Строгий контракт. `.proto` — единственный источник истины для Go edge и C++ core, генерация кода исключает расхождения.
4. HTTP/2 multiplexing. Один долгоживущий канал на под вместо тысяч TCP-соединений: меньше TLS-хендшейков, предсказуемее хвост задержки.
5. Богатые статусы (`UNAVAILABLE`, `DEADLINE_EXCEEDED`, `RESOURCE_EXHAUSTED`) позволяют отличить «нет ставки» от «сервис упал».

Campaign Service, наоборот, остаётся на REST/JSON.

1. Нагрузка не критична: 20–200 RPS и допустимые сотни миллисекунд. Выигрыш gRPC здесь равен нулю, а стоимость поддержки реальна.
2. Потребители — люди и браузер: кабинет через BFF, ручные интеграции. REST с OpenAPI — самый дешёвый способ.
3. Кеширование и условные запросы: `ETag`, `If-None-Match`, `Cache-Control` родные для HTTP и нужны BFF и CDN.
4. Bidding не зовёт Campaign синхронно: конфигурация приходит через Kafka и снапшот, gRPC-контракт не нужен.
5. Эволюция без генерации кода: новое поле не требует пересборки трёх клиентов.

Targeting тоже на gRPC: вызов идёт в критическом пути, дедлайн 5 мс, вызывается на каждый запрос. Разрешён hedged read — через 3 мс дублирующий запрос уходит в другой под, первый успешный выигрывает. Это допустимо только потому, что операция идемпотентна.

Billing, Statistics и Reporting работают через Kafka: их работа — следствие уже принятого решения, а не его причина.

Асимметрия здесь не случайна. Единый протокол «для красоты» стоит денег: gRPC в control plane не даёт выигрыша, а REST в горячем пути стоит миллисекунд на каждом запросе. Выбор диктуется профилем нагрузки.

### 3.4. Что не выбрано и почему

| Вариант | Почему отклонён |
|---|---|
| gRPC для всего, включая кабинет | gRPC-Web добавляет прокси, браузерная отладка хуже, выигрыша нет |
| REST для bid path | +5–10 % бюджета, отмена не доходит до ядра, контракт слабее |
| GraphQL для BFF | В control plane 3–4 ресурса; лишняя инфраструктура и риск дорогих запросов |
| SOAP/XML | Наследие, несовместимо с требованиями по задержке |
| Прямые вызовы сервис-сервис без gateway | Нет единой аутентификации, квот и измерения SLA |
| Service mesh как единственный шлюз | Mesh не аутентифицирует внешних партнёров и не даёт партнёрских квот |

## 4. Внешняя интеграция с DSP

### 4.1. Протокол

Наружу отдаём OpenRTB 2.6 поверх HTTPS с JSON-телом и `POST` на единый endpoint. Это стандарт индустрии: его поддерживают все крупные DSP/SSP, он описывает аукцион, таргетинг, креативы, приватные сделки и consent. Свободы выбора у AdScale нет — протокол диктует партнёр.

| Аспект | Решение | Комментарий |
|---|---|---|
| Транспорт | HTTPS (TLS 1.3), HTTP/2 где поддерживается | HTTP/1.1 допускается для совместимости |
| Формат | JSON, OpenRTB 2.6 | `application/json; charset=utf-8` |
| Метод | `POST /rtb/v2/bid` | Один endpoint на партнёра |
| Таймаут | `tmax` из запроса, но не более бюджета партнёра (80 мс) | Оба ограничения действуют одновременно |
| No-bid | `204 No Content` | Штатный сценарий, не ошибка |
| Версионирование | Путь (`/rtb/v2/`, `/rtb/v3/`) + `ext` | 3.0 включается отдельным маршрутом |
| Идентификация | `id` запроса, `imp.id`, `seat`, `crid` | Сквозной `auction_id` = trace id |
| Согласие | `regs.gdpr`, `user.ext.consent`, `regs.gpp` | Персонализация блокируется при отсутствии |
| Supply chain | `schain`, `sellers.json`, `ads.txt` | Проверка на gateway и в edge |

### 4.2. Почему не альтернативы

| Альтернатива | Оценка |
|---|---|
| **OpenRTB 3.0 (AdCOM)** | Строже, но поддержка площадок фрагментарна. Отдельный маршрут `/rtb/v3/` по готовности партнёра |
| **Проприетарный REST партнёра** | Возможен как исключение: адаптер под партнёра, ядро не меняется; дороже в поддержке |
| **gRPC наружу** | Партнёры не поддерживают; лишняя поверхность атаки |
| **XML/OpenRTB 2.3** | Устаревшая модель, нет deals/consent в нужном объёме |
| **WebSocket** | Усложняет балансировку и failover ради выигрыша 1–2 мс |

### 4.3. Антикоррупционный слой

Внешний протокол не должен протекать в ядро.

- Gateway проверяет структурную валидность и размер, не интерпретируя смысл.
- Bid Edge делает семантический маппинг: `imp` → внутренние `Impression`, `user.geo` → `GeoContext`, `regs` → `ConsentContext`, `device` → `DeviceContext`.
- Неизвестные поля OpenRTB попадают в телеметрию, а не отбрасываются молча.
- Ошибки маппинга — `400` с указанием поля, без доступа к нашим логам.
- Новый партнёр — это профиль конфигурации gateway плюс расширение маппинга, ядро не трогаем.

## 5. Kafka для событий кликов и показов

### 5.1. Почему Kafka

| Требование | Как Kafka закрывает |
|---|---|
| Приём 50 000+ событий/с без влияния на ответ | Последовательная запись в лог, батчинг, сжатие |
| Освободить 15–25 мс из бюджета отклика | Событие уходит после ответа пользователю |
| Потеря ≤ 0,01 % | `acks=all`, `min.insync.replicas=2`, идемпотентный producer |
| Несколько независимых потребителей | Statistics, Billing, Reporting, ML читают один поток в своих группах |
| Повторная обработка | Retention 7–30 дней и replay с любого offset |
| Порядок по кампании | Партиционирование по `campaign_id` |
| Буфер при пике | Потребитель может отстать, данные не теряются |
| Согласованность схем | Schema Registry, режим совместимости |
| Мультирегион | MirrorMaker 2 |

### 5.2. Почему не альтернативы

| Вариант | Почему отклонён |
|---|---|
| Синхронная запись в PostgreSQL (как сейчас) | 15–25 мс в критическом пути, write-конкуренция, потеря при сбое |
| Синхронный HTTP-вызов статистики | Тот же эффект плюс каскадный отказ |
| RabbitMQ | Очередь, а не лог: replay невозможен, пропускная способность ниже |
| Redis Streams | Данные в памяти, retention ограничен, нет Schema Registry и multi-region |
| AWS SQS/SNS | At-least-once без порядка, нет replay, привязка к облаку |
| Apache Pulsar | Технически сопоставим, но нет опыта, выше стоимость эксплуатации |
| Файлы на диске + агент | Ручная реализация партиций, репликации и consumer groups |

### 5.3. Модель событий

| Событие | Ключ | Гарантия | Объём (оценка) | Потребители |
|---|---|---|---|---|
| `impression.v1` | `campaign_id` | At-least-once, дедуп по `event_id` | до 12 000/с | Statistics, Billing, Reporting |
| `click.v1` | `campaign_id` | At-least-once, дедуп по `event_id` | 100–600/с | Statistics, Billing, ML |
| `spend.v1` | `campaign_id` | At-least-once из outbox Billing | до 12 000/с | Reporting, сверка |
| `bid.decided.v1` | `auction_id` | At-least-once, потеря телеметрии допустима | до 18 000/с | Analytics, ML |
| `campaign.changed.v1` | `campaign_id` | At-least-once, компакция | десятки/мин | Bidding, Adapter, Reporting |
| `deadline.exceeded.v1` | `partner_id` | At-least-once | редко | Observability, Reporting |

18 000 RPS × 86 400 с — это примерно 1,55 млрд запросов в сутки. Поэтому у каждого топика свой retention: сырые bid-события живут 24 часа, финансовые — 30 часов с компакцией, агрегаты хранятся в ClickHouse, а не в Kafka.

### 5.4. Гарантии и ограничения

- Семантика — at-least-once плюс дедупликация, то есть эффективно-однократная обработка. «Exactly-once» не используется: сквозного exactly-once между Kafka, PostgreSQL и внешним партнёром не существует.
- Идемпотентный producer защищает от дублей при ретраях внутри продюсера.
- Транзакции Kafka применяются только для read-process-write внутри одного сервиса.
- Outbox нужен для событий, которые публикуются вместе с изменением БД.
- DLQ забирает сообщения, не обработанные после N попыток; разбор ручной, replay — после исправления.
- Лаг мониторится, алерт срабатывает при отставании больше 60 с для финансовых топиков и больше 5 минут для аналитических.

## 6. Контракты и версионирование

| Контур | Формат контракта | Правила эволюции | Проверка |
|---|---|---|---|
| Внешний OpenRTB | JSON + JSON Schema | Только аддитивные изменения; версия в пути | Контрактные тесты на corpus партнёра |
| Внутренний sync | protobuf (`proto3`) | Не менять номера и типы полей; удаление — `reserved` | `buf breaking` в CI |
| Внутренний control plane | OpenAPI 3.1 | Аддитивные поля, `If-Match` | Схемная валидация, consumer-driven тесты |
| Kafka | Avro + Schema Registry | `BACKWARD_TRANSITIVE`; новое поле с default | CI-проверка при публикации схемы |
| Аналитика | Avro, версия в имени топика | Новая версия = новый топик | Dual-write на время миграции |

Контракт меняется раньше кода и независимо от него. Чужие таблицы БД не читает никто, только контракт — этим сервис и отличается от модуля монолита (ADR-001).

## 7. Паттерны надёжности

Отказоустойчивость означает предсказуемое поведение при отказе каждого элемента, а не просто «добавить retry». Общий принцип: лучше быстрый отказ или консервативное решение, чем опоздавший ответ и перерасход бюджета.

### 7.1. Бюджеты времени и отмена

| Правило | Реализация |
|---|---|
| Дедлайн вычисляется один раз на входе | `deadline = now + min(tmax, бюджет партнёра)` |
| Дедлайн передаётся во все синхронные вызовы | gRPC deadline + поле `deadline_epoch_ms` для ядра |
| Работа отменяется при исчерпании | `context.Cancel`, ядро проверяет дедлайн в цикле фильтрации |
| Guard за 15 мс до дедлайна | Немедленный `204` без новых дорогих операций |
| Таймаут дочернего вызова < остатка бюджета | Targeting 5 мс, Redis 4 мс, core 20 мс при бюджете 55 мс |

Отмена здесь работает как защита: при перегрузке отменённые запросы освобождают CPU, и очередь не растёт лавинообразно.

### 7.2. Circuit Breaker

Состояний три: `CLOSED` → `OPEN` (немедленный отказ) → `HALF_OPEN` (пробные запросы). Уровня два.

- Пассивный (Envoy/Istio): `outlier_detection` выбрасывает под по `5xx`, таймаутам и аномальной задержке, `circuit_breakers` ограничивают соединения и ожидающие запросы.
- Активный (в приложении): ловит семантические отказы, которых Envoy не видит, — например, targeting отвечает быстро, но пусто. Окно 10 с, минимум 20 запросов, порог 50 % ошибок, затем `OPEN` на 30 с и 5 пробных запросов.

| Зависимость | Таймаут | Порог открытия | Восстановление | Fallback |
|---|---|---|---|---|
| Targeting (gRPC) | 5 мс | 50 % / 10 с | 5 проб, 30 с | Сегменты из кеша → без сегментов |
| Auction Core (gRPC) | 20 мс | 20 % / 10 с | 5 проб, 15 с | `204` за 5 мс |
| Redis | 4 мс | 30 % / 10 с | 10 проб, 15 с | Локальный режим pacing |
| Campaign snapshot (REST) | 500 мс | 3 ошибки подряд | 30 с | Последний снапшот из БД |
| DSP Adapter → DSP | 10 с | 50 % / 60 с | 60 с | Очередь и повтор позже |
| Payment Gateway | 5 с | 50 % / 60 с | 60 с | `PENDING`, сверка |

Breaker не должен спасать от медленного ответа ценой его задержки: при открытии ответ формируется локально, а не ждёт таймаута.

### 7.3. Повторные попытки

`delay = min(cap, base × 2^attempt) × random(0.5, 1.0)`. Полный jitter обязателен, иначе повторы синхронизируются и создают вторую волну нагрузки.

| Сценарий | Повтор | Политика |
|---|---|---|
| Read вне критического пути (snapshot, конфигурация) | Да | 2 попытки, base 10 мс, cap 50 мс |
| Targeting в горячем пути | **Нет** | Hedge через 3 мс и fallback без сегментов |
| `POST /rtb/v2/bid` | **Нет** | Повтор создаёт второй аукцион и риск двойного расхода |
| Резерв бюджета в Redis | Да (идемпотентно) | 1 повтор, 2 мс |
| Публикация в Kafka | Да (идемпотентный producer) | Backoff 100 мс → 30 с в пределах буфера |
| Финансовое списание | Только с `Idempotency-Key` | 5 попыток, base 200 мс, cap 30 с, затем DLQ |
| DSP Adapter, платёжный шлюз | Да | 3 попытки, уважать `Retry-After`, проверка статуса |

Бюджет повторов — не больше 10 % общего числа запросов. Иначе при массовом сбое они усиливают нагрузку и окончательно валят зависимость.

Hedging вместо retry применяется только к идемпотентным read-вызовам Targeting: не более двух одновременных запросов и обязательная отмена проигравшего. Для записи и денег hedging запрещён.

### 7.4. Идемпотентность

Это единственный способ совместить at-least-once доставку с корректными деньгами.

| Операция | Ключ | Механизм | Результат повтора |
|---|---|---|---|
| Учёт показа | `event_id = hash(auction_id, imp_id, partner_id, ts_minute)` | Уникальный индекс, `ON CONFLICT DO NOTHING` | Дубль игнорируется |
| Учёт клика | `click_id` из подписанного URL | Уникальный индекс | Дубль игнорируется |
| Списание бюджета | `impression_id` | `ledger.unique(account_id, idempotency_key)` в одной транзакции с балансом | Возврат сохранённого результата |
| Резерв бюджета | `auction_id` | Поле в Redis-hash, TTL 30 с | Возврат существующего резерва |
| Создание кампании/бюджета | `Idempotency-Key` | Таблица ключей + хеш тела, TTL 24 ч | Сохранённый ответ; другое тело — `409` |
| Применение конфигурации | `version` кампании | Монотонная проверка `version > applied_version` | Старое событие игнорируется |

Порядок сообщений для этого не нужен. Финансовые операции аддитивны и дедуплицируются по ключу; партиционирование Kafka по `campaign_id` даёт локальность, но корректность держится на ключе, а не на очерёдности. Накопленные отклонения закрывает ежедневная сверка с расхождением не более 0,1 %.

### 7.5. Резервные стратегии: лестница деградации

Каждый уровень включается автоматически и помечает ответ (`X-Degraded`, `ext.as.degraded`), чтобы последствия были измеримы.

| Уровень | Условие | Что отдаём | Риск |
|---|---|---|---|
| **L0. Норма** | Все зависимости живы | Решение по актуальной конфигурации | — |
| **L1. Устаревший снапшот** | Лаг Kafka или недоступность Campaign | Последний снапшот (TTL до 15 мин) | Ставки по старым бюджетам |
| **L2. Кешированные ставки** | Redis недоступен | Локальный кеш решений (TTL 60 с), pacing 70 % | Недобор без перерасхода |
| **L3. Дефолтная политика** | Конфигурация недоступна | Фиксированная ставка по floor для whitelisted-кампаний | Низкая эффективность, доля ≤ 10 % |
| **L4. No-bid** | Всё остальное | `204` за 5 мс | Потеря аукционов, но SLA в норме |

Ограничения на всех уровнях: только кампании с подтверждённым бюджетом и положительной историей; лимит ≤ 10 % трафика и ≤ 5 % дневного бюджета; автоотключение через 15 минут; любая деградация — инцидент с алертом и записью в `degrade_event`.

Fallback никогда не выражается через `5xx`, ожидание, повторный вызов того же сервиса или ставку без проверки бюджета.

### 7.6. Изоляция и обратное давление

| Паттерн | Применение |
|---|---|
| **Bulkhead** | Отдельные пулы соединений на Targeting, Redis, Campaign |
| **Adaptive concurrency** | Лимит in-flight по задержке (AIMD), а не по CPU |
| **Load shedding** | При 90 % лимита конкурентности — `204` на входе |
| **Backpressure в Kafka** | Сначала теряется телеметрия, финансовые события не теряются |
| **Запрет каскада** | Нет вызова зависимости при открытом breaker |

### 7.7. Матрица деградации

| Что отказало | Критический путь | Учёт событий | Деньги | Видимость для партнёра |
|---|---|---|---|---|
| Targeting | Работает без сегментов | Норма | Норма | Возможно падение CTR |
| Redis | Консервативный pacing | Норма | Норма | Небольшой недобор |
| Auction Core | `204` | Норма | Норма | No-bid без ошибок |
| Kafka | Работает | Буфер 60 с, затем потеря телеметрии | Без потери: outbox + БД | Не заметно |
| Billing | Работает | Норма | Резерв без списания, сверка позже | Не заметно |
| Campaign Service | По снапшоту ≤ 15 мин | Норма | Норма | Постепенное устаревание ставок |
| API Gateway (одна AZ) | Через две другие | Норма | Норма | Кратковременные ошибки |
| Регион целиком (финал) | Failover через GSLB ≤ 5 мин | Репликация | RPO 0 | Возможны потери в пределах RTO |

|---|---|---|---|
| P-1 | gRPC для bid path | 55 мс бюджета, дедлайны, protobuf, Go+C++ | REST: +5–10 % задержки, нет отмены |
| P-2 | REST/JSON для control plane | 20–200 RPS, браузер, ETag | gRPC: не даёт выигрыша, дороже |

| P-4 | Kafka для событий | Буфер, replay, много потребителей | RabbitMQ/Redis/SQS: нет replay или дороже |
| P-5 | API Gateway (Envoy) | Auth, квоты, breaker, SLA-метрики | Nginx/Kong/cloud GW: см. api-gateway.md |
| P-6 | Outbox + идемпотентные потребители | Нет распределённых транзакций, деньги не теряются | 2PC: хрупок и недоступен между сервисами |
| P-7 | At-least-once + дедуп | Практичная и проверяемая гарантия | Exactly-once: невозможен сквозь границы |
| P-8 | Fallback до `204`, не `5xx` | Метрики партнёра и штрафы | `503`: партнёр считает ошибкой |

| P-10 | Hedged reads только для Targeting | Снижает P99.9 без побочных эффектов | Hedging для записи: двойные списания |

## 9. Риски и открытые вопросы

| Риск | Влияние | Смягчение |
|---|---|---|
| Партнёр подтвердит не OpenRTB 2.6, а иной формат | Задержка онбординга | ACL на edge, ядро не меняется |
| Kafka станет узким местом при 50 000 RPS | Лаг, потеря телеметрии | 64+ партиции, сжатие, батчинг, отдельные топики |
| Мало опыта gRPC в команде | Скорость разработки | Кодогенерация, шаблоны, `grpcurl`, обучение |
| Рост числа синхронных вызовов | Рост задержки | Бюджет на хоп, алерт на `sync_hops > 3` |
| Дефолтные ставки «залипнут» | Перерасход | TTL 15 мин, лимит 10 % трафика, автоотключение |
| Нет опыта эксплуатации Kafka и Redis | Нагрузка на команду | Managed-сервисы, runbook и алерты до запуска |

Открытыми остаются выбор облака или on-prem (влияет на managed Kafka), версия OpenRTB и `tmax` партнёра, требования по consent, необходимость `schain` и политика мультирегиона.
