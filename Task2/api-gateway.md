## 1. Назначение и границы

API Gateway — единственная точка входа внешнего трафика в AdScale. Он решает пять задач, и ни одна из них не относится к бизнес-логике.

| # | Задача | Почему именно на gateway |
|---|---|---|
| 1 | Терминация TLS/mTLS и аутентификация партнёра | Секреты и сертификаты не должны попадать в прикладные сервисы |
| 2 | Ограничение частоты и защита от перегрузки | Отсечение происходит до того, как запрос займёт CPU сервиса ставок |
| 3 | Circuit breaker и fail-fast | Решение «не звонить в сервис» принимается за микросекунды, до бизнес-кода |
| 4 | Маршрутизация и трансляция протокола | Партнёр говорит OpenRTB/JSON, внутри — gRPC; миграция требует переключения |
| 5 | Измерение SLA по каждому партнёру | Штрафы считаются по нашим метрикам, измерения — до и после upstream |

### 1.1. Чего gateway не делает

| Не делает | Где это должно быть |
|---|---|
| Не интерпретирует аукцион и не считает ставку | Bidding Service |
| Не ходит в БД/Redis за бизнес-данными | Bidding Service; только Redis для счётчиков лимитов |
| Не повторяет `POST /bid` при ошибке | Нигде: повтор создаёт второй аукцион |
| Не модифицирует тело ответа | Bidding Service |
| Не выполняет роль service mesh между внутренними сервисами | Istio sidecar/mTLS |

Граница проходит так: если для решения нужны данные о кампаниях, бюджетах или пользователях — это не gateway. Если хватает метаданных соединения (ключ, сертификат, IP, заголовки, частота) — это gateway.

## 2. Требования

| Категория | Требование | Источник |
|---|---|---|
| Пропускная способность | 18 000 RPS (промежуточно), 50 000 RPS (финал); новая DSP — 3 000 RPS | Контекст задачи |
| Собственная задержка | ≤ 2 мс P99, ≤ 3 мс P99.9 (включая TLS-сессию) | Бюджет 80 мс |
| Доступность | 99,95 % (не хуже платформенных 99,9 %) | Drivers |
| Ответ без ошибок | ≥ 99,95 %, потеря по тайм-ауту ≤ 0,5 % | Drivers |
| SLA партнёра | 99,5 % запросов с ответом ≤ 80 мс | Контекст задачи |
| Безопасность | mTLS, ротация ключей, IP allowlist, WAF, защита от DDoS/amplification | Drivers, P1 |
| Изоляция партнёров | Квота одного партнёра не влияет на другого | Требование справедливости |
| Наблюдаемость | P50/P95/P99/P99.9 по партнёру, разложение задержки, трассировка | Drivers, P0 |
| Управляемость | Новый партнёр — конфигурация, не релиз кода | P1, ≤ 5 дней |

## 3. Выбор продукта

### 3.1. Сравнение

| Критерий | **Envoy (+ Istio ingress)** | Kong | NGINX / OpenResty | Облачный API GW | HAProxy |
|---|---|---|---|---|---|
| Собственная задержка | < 1 мс P99 | 1–2 мс (Lua) | < 1 мс | 3–10 мс + внешний хоп | < 1 мс |
| Circuit breaker | Да (outlier detection) | Плагин | Нет, только `max_conns` | Частично | Нет |
| Динамическая конфигурация без reload | Да (xDS) | Да | Reload/`balancer_by_lua` | Да | Reload |
| Глобальные лимиты (Redis) | Да (RLS + Redis) | Да (плагин) | Своя разработка | Ограниченно | Своя разработка |
| Трансляция JSON → gRPC | Да (`grpc_json_transcoder`) | Плагин | Своя разработка | Частично | Нет |
| mTLS/mesh-совместимость | Родная (Istio) | Отдельный слой | Нет | Нет | Нет |
| Стоимость при 1,5 млрд запросов/сутки | Своя инфраструктура | Своя | Своя | **Оплата за запрос** | Своя |
| Наблюдаемость | OTel, Prometheus нативно | Плагины | Модули | Готовая, но закрытая | Метрики |
| Порог входа | Средний | Низкий | Средний | Низкий | Низкий |

### 3.2. Решение

Выбран Envoy как edge-прокси (Ingress Gateway) с Rate Limit Service на Redis. На промежуточном этапе это самостоятельный ingress без полного Istio, на финальном — ingress того же Istio, который обеспечивает mTLS между сервисами.

Причины:

1. Один компонент закрывает четыре требования — маршрутизацию, лимиты, breaker и трансляцию — без плагинов и собственного кода.
2. Платы за запрос нет. При 1,5 млрд запросов в сутки облачный API Gateway стоил бы кратно больше всей остальной инфраструктуры.
3. Задержка. Envoy — C++-прокси с минимальным оверхедом; Lua-плагины Kong добавляют миллисекунды, которых в бюджете 80 мс уже нет.
4. Путь к финальной архитектуре. Тот же продукт станет ingress для Istio: не придётся менять шлюз и переписывать конфигурацию квот.
5. Динамическая конфигурация. Квота или маршрут применяются через xDS без reload — без этого «подключение за 5 дней» не получится.
6. Прозрачность для разбора SLA: нативные гистограммы, метрики `upstream_*`, `Server-Timing`.

Отвергнуты Kong (лишний слой и Lua-задержка, breaker и лимиты всё равно через плагины), NGINX/OpenResty (breaker, лимиты и трансляцию в gRPC писать самим — скрытая стоимость), облачный API Gateway (цена за запрос, vendor lock-in, вариативная задержка) и HAProxy (нет breaker'а по коду ответа и трансляции).

## 4. Топология

Визуальная схема — [diagrams/C4_Deployment_EdgeTopology.puml](diagrams/C4_Deployment_EdgeTopology.puml).

| Принцип | Реализация |
|---|---|
| Разделение путей | Отдельные listeners и пулы: `bid` (JSON→gRPC), `beacon` (HTTP, Kafka через Collector), `admin` (OAuth2/OIDC) |
| Симметрия по AZ | По одному экземпляру в каждой AZ, `topologySpreadConstraints`, anti-affinity |
| Отсутствие общего состояния | Gateway stateless; общее состояние — только счётчики лимитов в Redis |
| Близость к upstream | `prefer-local-az`: пересечение AZ добавляет 0,5–1 мс |
| Долгоживущие соединения | HTTP/2 keep-alive до upstream, TLS-резюмирование для партнёров |
| Отдельный путь для beacon | Всплеск кликов (до 60 000 RPS) не конкурирует с аукционом за лимиты и пулы |

## 5. Маршрутизация

### 5.1. Правила

| Правило | Значение |
|---|---|
| Внешний endpoint | `POST https://rtb.adscale.example/rtb/v2/bid` — единый для всех партнёров |
| Идентификация партнёра | mTLS-сертификат + API-ключ `X-Api-Key`; результат — доверенный `X-Partner-Id` |
| Маршрут | `partner_id → cluster` (bid-v2) с весами по версиям |
| Таймаут маршрута | `min(tmax, partner_budget) − gateway_overhead`; передаётся upstream как gRPC deadline |
| Заголовки upstream | `X-Partner-Id`, `X-Request-Id`, `X-Deadline-Ms`, `X-Trace-Id`, `traceparent` |
| Заголовки downstream | `X-Config-Version`, `X-No-Bid-Reason`, `X-Response-Time-Ms`, `Server-Timing` |
| Ограничение тела | 64 КБ, больше — `413` без чтения тела целиком |
| Ограничение `imp` | 8 объектов, больше — `400` (защита от amplification) |

### 5.2. Миграция по Strangler Fig

На промежуточном этапе главная функция gateway — управляемое переключение между монолитом и новым сервисом ставок без изменения контракта для партнёра.

| Этап | Веса маршрутов | Условие перехода дальше |
|---|---|---|
| 0. Baseline | 100 % → `monolith-bid` | Всё работает как раньше |
| 1. Shadow | 100 % → monolith, копия 1 % → `bidding-v2` | Расхождение ставок ≤ 5 %, ошибок нет |
| 2. Canary | 95/5 по `partner_id` | P99 нового контура ≤ 35 мс, no-bid ≤ 0,5 % |
| 3. Ramp | 50/50, затем 100 % → `bidding-v2` | Три часа без деградации, сверка расхода ≤ 0,1 % |
| 4. Drain | Старый контур только для отката | 7 дней стабильности |

Партнёр закрепляется за контуром: если он «прыгает» между контурами, ломаются сверка и кеш. Откат — одна операция через xDS за секунды, без перезапуска. Канареечный релиз версии идёт 1 % → 5 % → 25 % → 100 % с автооткатом по SLO, в финале добавляется гео-маршрутизация в ближайший регион (RTO ≤ 5 мин). Маршрутизация по содержимому запрещена: она добавляет задержку и делает поведение непредсказуемым.

## 6. Аутентификация и авторизация

### 6.1. Схема

| Слой | Механизм | Стоимость на запрос |
|---|---|---|
| Транспорт | mTLS: сертификат партнёра от нашего CA | 0 после handshake (резюмирование) |
| Партнёр | API-ключ `X-Api-Key` (32 байта, префикс `pk_`), привязан к `partner_id` | Локальный кеш ключей, O(1), без сети |
| Сеть | IP allowlist для партнёров со статическими диапазонами | Сравнение по префиксному дереву |
| Админ-API | OAuth2 client credentials, JWT на 15 мин, RBAC | Проверка подписи по локальному JWKS, кеш 5 мин |
| Внутренние вызовы | mTLS + JWT сервисной учётной записи (SPIFFE в финале) | Sidecar |

### 6.2. Требования

1. Удалённых проверок в горячем пути нет. Ключи и JWKS кешируются локально с TTL 60 с; отзыв применяется максимум за 60 с, аварийно — принудительной инвалидацией через pub/sub.
2. Ротация без простоя: два активных ключа на партнёра, сертификаты с перекрытием 30 дней.
3. Ошибки не различают причину: `401` на любое несоответствие, детали — только в наших логах с `X-Request-Id`.
4. Аудит: изменения ключей, квот и маршрутов пишутся в append-only лог с актором и трассировкой.
5. `partner_id` из аутентификации — единственный доверенный источник. Заголовок `X-Partner-Id`, пришедший от партнёра, перезаписывается.
6. Защита от подмены и DDoS: проверка `Host`/`Content-Type`, отключение `OPTIONS`/`TRACE`, HSTS, TLS 1.3, лимит соединений на IP, WAF.

### 6.3. Почему не подпись тела (HMAC) на bid path

OpenRTB не предусматривает подписи запроса, а HMAC по 3 КБ стоит 50–150 мкс и требует синхронизации секретов. Для аукционного трафика достаточно mTLS, ключа и allowlist: канал защищён на транспорте, ключ не передаётся открыто, а replay ничего не даёт — аукцион уже прошёл. HMAC оправдан для финансовых API, там он и применяется.

## 7. Ограничение частоты

### 7.1. Модель лимитов

| Уровень | Что ограничивается | Пример для новой DSP | Где считается |
|---|---|---|---|
| L1. Соединения | Параллельные соединения с IP | 200 | Envoy, локально |
| L2. Партнёр, RPS | Устойчивая частота | 3 000 RPS | RLS + Redis, глобально |
| L3. Партнёр, burst | Кратковременный всплеск | 3 600 (×1,2) | Token bucket |
| L4. Партнёр, конкурентность | In-flight запросы | 2 000 | Envoy, локально |
| L5. Под | Запросы в обработке | adaptive concurrency | Envoy + приложение |
| L6. Админ-API | Частота операций | 50 RPS на клиента | RLS |
| L7. Beacon | События в секунду | 60 000 RPS | Отдельный listener |
| L8. Глобальный предел | Суммарный вход | 20 000 RPS (промежуточно) | RLS |

### 7.2. Алгоритм

Схема — token bucket на партнёра плюс скользящее окно для аудита.

- Ёмкость ведра равна burst, скорость пополнения — контрактному RPS.
- Проверка двухуровневая: локально (Envoy, точность ±5 %) отсекает всплеск без сетевого хопа, глобально (RLS + Redis, ±1 %) держит квоту между AZ.
- В Redis уходит один `EVALSHA` с ключом `rl:{partner_id}:{minute}`, цена ≤ 0,3 мс. Если Redis недоступен, работает fail-open с локальным лимитом 70 %: лучше отдать часть трафика, чем остановить партнёра.
- Ключ лимита — `partner_id`, а не IP: у крупных DSP трафик приходит с десятков адресов.

### 7.3. Поведение при превышении

| Путь | Ответ | Почему |
|---|---|---|
| Bid path | `204` + `X-No-Bid-Reason: rate_limited` за ≤ 1 мс | `429` партнёр считает ошибкой и может применить санкции |
| Admin API | `429` + `Retry-After` + `X-RateLimit-*` | Нужен явный сигнал клиенту |
| Beacon | `429` (браузер повторит) | Отказ с ретраем корректнее молчаливой потери |

### 7.4. Справедливость и приоритеты

- Партнёры изолированы: лимиты и пулы соединений у каждого свои.
- Классы приоритета: `P0` — платный трафик DSP, `P1` — внутренние тесты, `P2` — shadow. При перегрузке отбрасывается низший класс.
- Brownout вместо отказа: у предела платформы gateway снижает `P2` и `P1`, сохраняя `P0` в SLA.
- Приоритета по ожидаемой выручке на gateway нет: для него нужны данные аукциона, которых на входе не существует.

## 8. Автоматический размыкатель

### 8.1. Три уровня защиты

| Уровень | Механизм | Что ловит | Реакция |
|---|---|---|---|
| **Пассивный** | Envoy `outlier_detection` | `5xx`, таймауты, аномальная задержка пода | Выброс пода из балансировки на 30 с (до 300 с) |
| **Активный** | Envoy `circuit_breakers` | Исчерпание соединений, очередей, ретраев | Немедленный отказ новым запросам |
| **Адаптивный** | Adaptive concurrency (AIMD) | Рост задержки у «колена» | Снижение лимита in-flight до восстановления P99 |

### 8.2. Параметры

| Параметр | Значение | Обоснование |
|---|---|---|
| `consecutive_5xx` | 5 | Быстрое отсечение сбойного пода |
| `interval` | 10 с | Окно наблюдения |
| `base_ejection_time` | 30 с | Достаточно для рестарта пода |
| `max_ejection_percent` | 50 % | Защита от выброса всего кластера |
| `max_pending_requests` | 200 | Очередь не должна расти: ожидание = просроченный ответ |
| `max_retries` | 0 для bid | Повтор POST создаёт второй аукцион |
| `timeout` | остаток бюджета | Дедлайн, а не фиксированное значение |

### 8.3. Что происходит при размыкании

1. Gateway перестаёт отправлять запросы в разомкнутый кластер.
2. Ответ формируется на gateway: `204` с `X-No-Bid-Reason: circuit_open` за 1–2 мс.
3. Если настроен fallback-кластер (монолит на этапе миграции) — запрос идёт туда, но только если остаток бюджета больше 20 мс.
4. Half-open: 5 пробных запросов, при успехе — возврат в строй, при неудаче — повторное размыкание с удвоенным интервалом.

### 8.4. Почему breaker на gateway, а не только в сервисе

Сервис ставок тоже имеет breaker (Targeting, Redis, ядро), но к этому моменту он уже потратил бюджет на приём, разбор и маршрутизацию. Gateway размыкается до этих затрат и не даёт очереди накопиться. Уровни дополняют друг друга: gateway страхует от «сервис недоступен», сервис — от «зависимость деградировала».

## 9. Мониторинг времени отклика

### 9.1. Метрики

| Метрика | Тип | Назначение |
|---|---|---|
| `gateway_request_duration_seconds{partner,route,code}` | гистограмма | P50/P95/P99/P99.9, SLA-отчётность |
| `gateway_upstream_duration_seconds{cluster,pod}` | гистограмма | Отделить нашу задержку от задержки сервиса |
| `gateway_own_overhead_seconds` | гистограмма | Собственная стоимость gateway (цель ≤ 2 мс P99) |
| `gateway_breaker_state{cluster}` | gauge | closed/open/half-open |
| `gateway_rate_limited_total{partner,reason}` | счётчик | Доля отбракованного трафика |
| `gateway_inflight_requests{cluster}` | gauge | Насыщение |

### 9.2. Разложение задержки

Ключевой инструмент разбора SLA-инцидента — атрибуция времени через `Server-Timing` (`edge;dur`, `upstream;dur`) и `X-Response-Time-Ms`.

| Сегмент | Как измеряется | Кто отвечает |
|---|---|---|
| Сеть партнёр → edge | Разница по `tcp_info`/RTT-оценке, пассивно | Партнёр/сеть |
| Gateway | `edge;dur` | Мы |
| Upstream (edge + core) | `upstream;dur` | Мы (сервис ставок) |
| Ответ edge → партнёр | По `X-Response-Time-Ms` на стороне партнёра | Партнёр/сеть |

С этим разложением на вопрос «кто виноват» можно ответить фактами, а не оценками, и это же защищает от необоснованных штрафов.

### 9.3. SLO и алерты

| SLI | SLO | Алерт |
|---|---|---|
| Доля ответов ≤ 80 мс | ≥ 99,5 % за 30 дней | Burn rate: 14,4× за 1 ч, 6× за 6 ч |
| Доля `5xx` | ≤ 0,01 % | > 0,05 % за 5 мин |
| Доля тайм-аутов | ≤ 0,1 % | > 0,2 % за 5 мин |
| Собственная задержка gateway | P99 ≤ 2 мс | > 3 мс за 10 мин |
| Доля rate limited | ≤ 0,5 % | > 2 % за 10 мин |
| Доступность | 99,95 % | Любой простой > 1 мин |

Дашборды: общий SLA по партнёрам; по партнёру (RPS, перцентили, коды, лимиты, breaker); ёмкость и насыщение; разложение задержки.

### 9.4. Трассировка и синтетический мониторинг

- Gateway генерирует `traceparent`, если его нет, и передаёт дальше; `auction_id` = `trace_id`.
- Tail-based sampling: 100 % ошибок и запросов > 60 мс, 1 % успешных. Логи без PII.
- «Канареечный» клиент раз в 10 с отправляет эталонный bid request от имени каждого партнёра и проверяет код ответа, задержку и `X-Config-Version`. Это единственный способ заметить сломанный маршрут в часы низкой нагрузки.

## 10. Ёмкость и развёртывание

| Параметр | Значение | Обоснование |
|---|---|---|
| Пропускная способность пода | 3 000 RPS при P99 ≤ 2 мс, 4 vCPU | TLS-резюмирование, HTTP/2, без Lua |
| Утилизация цели | ≤ 60 % | Запас на всплеск и выбытие AZ |
| Промежуточное решение | 9 подов (3 на AZ), HPA 6–15 | 27 000 RPS ёмкости против 18 000 |
| Финальное решение | 24 пода, HPA 18–40 | 72 000 RPS против 50 000 |
| Ресурсы на под | 4 vCPU, 2 ГБ, 25 Гбит/с NIC | — |
| Обновление | RollingUpdate `maxUnavailable=1` на AZ | Ёмкость не падает ниже 66 % |

HPA масштабирует по RPS и по P99 собственной задержки. При деградации upstream поды не должны размножаться и усиливать перегрузку, поэтому рост задержки наоборот ограничивает приём через adaptive concurrency.

## 11. Онбординг новой DSP (чек-лист, 5 дней)

| День | Шаг | Результат |
|---|---|---|
| 1 | Контракт: версия OpenRTB, `tmax`, лимиты, форматы, consent, `schain` | Согласованная спецификация |
| 1 | mTLS-сертификат, API-ключ, IP allowlist | Подключение к staging |
| 2 | Профиль маршрута и квоты (3 000 RPS, burst 3 600, concurrency 2 000) | Конфигурация в git, применена через xDS |
| 2 | Контрактные тесты на corpus реальных запросов | Отчёт о совместимости |
| 3 | Shadow-трафик 1 %, сравнение с эталоном | Расхождение ставок ≤ 5 % |
| 4 | Нагрузочный тест 3 000 RPS: P95/P99, breaker, лимиты | P99 ≤ 70 мс, `5xx` = 0 |
| 5 | Канарейка 5 % → 100 %, дашборд, алерты, runbook | Партнёр в продакшене |

Всё, кроме контрактных тестов и, при необходимости, расширения маппинга, — конфигурация, а не код. Это и есть проверка требования «подключение за 5 дней без правки ядра».

## 12. Режимы деградации

| Отказ | Поведение gateway | Влияние на партнёра |
|---|---|---|
| Один под bid-сервиса | Выброс из балансировки, трафик на остальные | Не заметно (P99 +1–2 мс) |
| Все поды bid-сервиса | Breaker открыт → `204` за 2 мс | No-bid, метрики ошибок чистые |
| Одна AZ | GSLB выводит AZ, трафик на две другие | Кратковременные ошибки при переключении |
| Redis (лимиты) | Fail-open с локальным лимитом 70 % | Часть трафика может быть отброшена |
| RLS недоступен | Локальные лимиты Envoy продолжают работать | Небольшое превышение квоты |
| Перегрузка платформы | Brownout `P1`/`P2`, adaptive concurrency | Приоритетный трафик в SLA |
| DDoS | Лимиты на IP/соединения, WAF | Легитимный трафик в квоте не страдает |
| Ошибка конфигурации маршрута | Валидация в CI + canary + автооткат по `5xx` | Не более 1 % трафика на время отката |

## 13. Безопасность и комплаенс

| Требование | Реализация |
|---|---|
| Шифрование | TLS 1.3, ограниченный набор шифров, HSTS, mTLS для партнёров |
| Секреты | Vault/KMS, ротация, отсутствие секретов в конфигурации и логах |
| PII | Тело запроса не логируется; IP — только агрегированно; consent-поля передаются без изменений |
| Consent | `regs` обязательно; при отсутствии персонализация блокируется в сервисе, а не на gateway |
| Аудит | Все изменения маршрутов, квот и ключей — append-only лог |
| Доступ персонала | Отдельный admin-listener, OIDC, RBAC, MFA, отдельная сеть |
| Уязвимости | Сканирование образов, минимальный базовый образ, подпись образов |

## 14. Итоговые решения

| # | Решение | Кратко |
|---|---|---|
| G-1 | Envoy как edge-gateway | Нулевая задержка, breaker и лимиты «из коробки», путь к Istio |
| G-2 | Единый endpoint `/rtb/v2/bid` | Партнёр определяется ключом, контракт стабилен при миграции |
| G-3 | mTLS + API-ключ, локальная проверка | Без удалённых вызовов в горячем пути |
| G-4 | Двухуровневые лимиты (local + RLS/Redis) | Точность глобальной квоты и скорость локального отсечения |
| G-5 | `204` вместо `429`/`5xx` на bid path | Не портить метрики партнёра, не провоцировать повторы |
| G-6 | Breaker на gateway и в сервисе | Защита до и после затрат бюджета |
| G-7 | Обязательный `Server-Timing` и `auction_id`=trace | Разбор SLA фактами |
| G-8 | Онбординг через конфигурацию | 5 дней без релиза кода |
