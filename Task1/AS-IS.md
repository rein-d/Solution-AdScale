# Анализ текущей архитектуры AdScale

## 1. Что известно о системе

| Показатель | Значение |
|---|---|
| Пиковая нагрузка | 15 000 запросов в секунду |
| Требование к времени отклика | не более 100 мс |
| Фактическое время отклика | 110–120 мс у 95 % запросов |
| Запас производительности | отсутствует |
| Серверов базы данных | 1, резервных копий и реплик в схеме нет |
| Компонентов, обращающихся к базе | 6 |
| Кеш | отсутствует |
| Очереди и буферы записи | отсутствуют |
| Обновление системы | вручную, без контейнеризации |

## 2. Где система упирается в потолок

### 2.1. Одна база на все задачи

К базе одновременно подключены шесть компонентов: выдача рекламы, аукцион, статистика, финансы, аналитика и кабинет рекламодателя. Один запрос пользователя порождает от трёх до шести обращений к базе — чтение таргетинга, чтение ставок, запись показа и служебные запросы. При 15 000 запросов в секунду это 45–90 тысяч операций в секунду на одном сервере. Если поток удвоится, удвоятся и операции: второго сервера, реплик и кеша в схеме нет, поэтому остаётся только поставить машину мощнее, а у этого пути есть физический предел.

### 2.2. Аналитика идёт на рабочей базе

Отчёты строятся на тех же ресурсах, что и выдача рекламы. Тяжёлый запрос держит процессор и соединения, а запросы на показ в это время ждут. Отсюда замедления, которые не совпадают с пиками трафика: их вызывает не нагрузка, а чей-то отчёт.

### 2.3. Учёт показа стоит в критическом пути

Событие показа записывается до того, как пользователь получит ответ, хотя на содержимое баннера эта запись никак не влияет. По оценке, она занимает 15–25 мс из 100 — до четверти отведённого времени. Если модуль статистики не отвечает дольше тайм-аута, баннер не показывается вообще. Очереди и буфера нет, поэтому события, не записанные в момент сбоя, теряются безвозвратно.

### 2.4. Кеша нет

Каталог кампаний и ставки меняются редко, но читаются из базы на каждый запрос — два чтения на запрос, порядка 30 000 чтений в секунду в пике. Каждое из них идёт на диск и в сеть вместо памяти.

### 2.5. Резервирования нет

Каждый компонент существует в одном экземпляре. Запрос последовательно проходит четыре звена: сервер объявлений, аукцион, модуль показа, модуль статистики. При надёжности каждого звена 99,9 % вся цепочка даёт 99,6 %, то есть около 3,5 часов недоступности в месяц; с учётом единственной базы реальная цифра будет хуже. Порядок восстановления нигде не зафиксирован, всё делается руками.

## 3. Точки отказа

| Что отказывает | Последствия | Восстановление |
|---|---|---|
| База данных | Останавливаются выдача, статистика, финансы и кабинет одновременно | Ручное, регламент не задан |
| Аукционный модуль | Показ рекламы прекращается, выручка останавливается | Ручное |
| Сервер объявлений | Партнёры получают ошибки, трафик не обрабатывается | Ручное |
| Модуль показа | Баннеры не отображаются | Ручное |
| Модуль статистики | Остановка показов вместе со сбором данных, потеря событий | Ручное |
| Аналитический модуль | Тяжёлый отчёт замедляет выдачу рекламы | Ручное прерывание запроса |
| Ошибка при обновлении | Сбой компонента из-за ручного развёртывания | Ручной откат |

## 4. Время отклика

| Этап | Время, мс |
|---|---|
| Сеть и приём запроса | 5–10 |
| Приём, определение пользователя, подбор кандидатов | 20–30 |
| Проведение аукциона | 25–35 |
| Формирование баннера | 10–20 |
| Учёт показа | 15–25 |
| Служебные переходы | 10–15 |
| **Итого** | **85–135** |

Требование — не более 100 мс, расчётная сумма — 85–135 мс. Даже в хорошем сценарии остаётся 15 мс запаса, и любая задержка базы сверх расчётной выводит ответ за границу. В пиковые часы к обработке добавляется ожидание в очереди к базе, поэтому отклик растёт быстрее, чем нагрузка.

Для аукциона это не только нарушение метрики. Ответ, пришедший после тайм-аута партнёра, в торгах не участвует — запрос уходит неоплаченным.

## 5. Влияние на бизнес

| Риск | Последствие | Основание |
|---|---|---|
| Превышение времени отклика | Штрафы по договорам, потеря запросов в аукционе | 110–120 мс против 100 мс |
| Отказ базы данных | Полный простой и остановка выручки | один сервер без резерва |
| Потеря событий показов | Расхождения в отчётности и расчётах | запись без очереди и буфера |
| Ошибка ручного обновления | Внеплановый простой | обновление вручную |
| Рост трафика | Удвоение операций с базой на том же сервере | 45–90 тыс. операций в секунду уже сейчас |
| Замедления вне пиков | Непредсказуемое качество, отток партнёров | отчёты на рабочей базе |

## 6. Что из этого следует

Систему ограничивают три вещи. Вся нагрузка лежит на одном сервере базы. Учёт показов стоит в критическом пути и съедает 15–25 % бюджета отклика. Ни у одного компонента нет резервного экземпляра.

Первые две определяют, уложимся ли мы в 100 мс, третья — как долго будет длиться простой. Оптимизация отдельного модуля эти три показателя не сдвинет: нужно разнести нагрузку по серверам, вынести учёт событий из ответа пользователю и зарезервировать компоненты.
