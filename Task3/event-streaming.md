# Потоковая обработка (Kafka)

**Статус:** рабочая версия  
**Схемы:** [diagrams/Sequence_EventPipeline.puml](diagrams/Sequence_EventPipeline.puml), [diagrams/C4_Deployment_DataTopology.puml](diagrams/C4_Deployment_DataTopology.puml)

## 1. Зачем Kafka

Kafka — единственный асинхронный контур AdScale и граница между критическим путём и всем остальным. Она нужна, чтобы:

1. **не учитывать событие в ответе пользователю.** Сейчас запись показа занимает 15–25 мс из 100 и может потеряться при сбое;
2. **переживать пики и отставание потребителей.** 1,5–4,3 млрд сообщений в сутки синхронно не обработать;
3. **дать нескольким потребителям читать один поток независимо.** У Statistics, Billing, Reporting, Analytics и ML свой темп;
4. **иметь источник для replay.** Пока событие в Kafka, его можно переиграть после исправления ошибки.

Что важно не нарушить: потеря событий ≤ 0,01%, деньги не теряются, строгий порядок по кампании не обязателен (но желателен), финансовая обработка идемпотентна, а контур не влияет на P95 55 мс.

## 2. Роль Kafka

| Контур | Что делает | Чего не делает |
|---|---|---|
| **Буфер приёма** | Принимает события от Event Collector (`acks=all`), хранит 24 ч – 7 дней | Не хранилище отчётности |
| **Шина событий** | Доставляет изменения конфигурации, решения, расходы | Не заменяет синхронные API |
| **Источник replay** | Позволяет пересобрать витрины и восстановить ClickHouse | Не резервная копия финансового ledger |
| **Разделитель контуров** | Отделяет hot path от статистики, биллинга и аналитики | Не участвует в решении по ставке |

Граница простая: bid request Kafka не ждёт. Событие публикуется после ответа или через outbox после коммита БД. Если Kafka недоступна, аукцион продолжается; теряется телеметрия, деньги защищены outbox и ledger.

## 3. Топология кластера

### 3.1. Развёртывание

| Параметр | 3 месяца | 12 месяцев | Зачем |
|---|---|---|---|
| Брокеры | 6 (по 2 в каждой AZ) | 9–12 | RF=3 и `minISR=2` требуют минимум 3; 6 дают запас на выбытие AZ |
| Контроллер | KRaft, 3 контроллера | KRaft, 3 контроллера | Без ZooKeeper, меньше компонентов и быстрее failover |
| Диск | NVMe, 3 ТБ на брокер | 6 ТБ на брокер | Retention 7 дней и запас ~30% |
| Сеть | 10 GbE | 25 GbE | До ~85 000 msg/с |
| RF / minISR | 3 / 2 | 3 / 2 | Пережить отказ брокера без остановки записи |
| `unclean.leader.election` | `false` | `false` | Лучше недоступность партиции, чем потеря финансовых событий |
| Сжатие | `zstd` | `zstd` | Меньше диск и сеть (примерно в 3–4 раза) |
| Tiered storage | Для `bid.decided` | Для `impression`, `click`, `bid.decided` | Долгая история в S3 без SSD-стоимости |

### 3.2. Почему Kafka

| Вариант | Почему не берём |
|---|---|
| Синхронная запись в PostgreSQL (как сейчас) | 15–25 мс в критическом пути, конкуренция с OLTP, потеря при сбое |
| RabbitMQ | Очередь, не лог: после ack сообщение удаляется, replay нет; пропускная способность ниже |
| Redis Streams | Данные в памяти, retention ограничен, нет Schema Registry/мультирегиона |
| AWS SQS/SNS | At-least-once без порядка и replay, привязка к облаку (инфра ещё не выбрана) |
| Apache Pulsar | Сопоставим, но дороже/сложнее в эксплуатации при текущей команде |
| Файлы и агент | Пришлось бы самим делать партиции, репликацию, группы, replay |
| HTTP-вызов Statistics | Каскадный отказ: недоступность статистики остановит показы |

Обоснование совпадает с [interaction.md §5.1–5.2](../Task2/interaction.md#51-почему-kafka), здесь уточняем топологию и хранение.

### 4.3. Почему у топиков разные retention

| Класс | Retention | Причина |
|---|---|---|
| Сырые события (impression, click) | 7 дней | Хватает для replay после сбоя и восстановления ClickHouse; дальше — S3 Parquet |
| Телеметрия решений | 24 часа | Объём максимальный (1,5–4,3 млрд/сутки), ценность диагностическая; выборка 0,1% уходит в S3 |
| Финансовые события | 30 часов и компакция | Нужна последняя версия расхода по кампании и окно для повторной обработки; долгая история — ledger и ClickHouse |
| Конфигурация | Компакция без срока | Потребитель, пропустивший неделю, должен получить актуальную конфигурацию |
| DLQ | 14–30 дней | Время на разбор и исправление; финансовые — 30 дней |

**Почему не 30 дней на всё.** При 4,3 млрд сообщений/сутки и 150–250 байтах на сообщение это сотни гигабайт в сутки без сжатия. Kafka — не data lake. Долгая история живёт в S3 (Parquet) и ClickHouse.

## 5. Схемы событий

### 5.1. Avro, а не JSON

| Критерий | JSON без схемы | JSON + JSON Schema | **Avro + Schema Registry** |
|---|---|---|---|
| Размер сообщения | 100 % | 100 % + имена полей | 20–40 % (бинарный, без имён) |
| Стоимость CPU на 1,5 млрд/сутки | Высокая | Высокая | Низкая |
| Эволюция | Не контролируется | Валидация есть, совместимость вручную | `BACKWARD_TRANSITIVE`, проверка в CI |
| Обязательность полей | Нет | Есть, но слабая | Есть, с default и nullable |
| Экосистема | Любая | Любая | Kafka, Connect, Flink, ClickHouse |
| Отладка | Проще | Проще | `kcat`/Console и Schema Registry UI |

**Выбор: Avro и Schema Registry, режим `BACKWARD_TRANSITIVE`.** JSON оставляем там, где его требует внешняя сторона: OpenRTB на границе с DSP и тела ошибок DLQ для ручного разбора. Внутри шины — бинарный Avro.

Правила эволюции:

1. Новое поле — только с `default`; удаление — только после двух релизов и через nullable.
2. Нельзя менять тип и номер поля; переименование — только через alias.
3. Схема публикуется до кода; CI блокирует несовместимое изменение.
4. Версия схемы дублируется в заголовке (`schema_version`) для диагностики, но истина — в Schema Registry по `subject`.

### 5.5. PII и consent

- `user_hash` — HMAC с версией соли. При ротации соли старые хеши не пересчитываются, версия едет в сообщении.
- Raw IP, email, телефон и точная геолокация не публикуются.
- `consent.personalization_allowed = false` — потребители не должны использовать событие для персонализации. Поле проверяется в схеме/контрактных тестах.
- Регуляторные требования (маркировка рекламы) добавляются аддитивными полями, не новым топиком.

## 6. Группы потребителей

### 6.1. Список групп

| Группа | Топики | Что делает | Параллелизм (3 мес) | SLO лага | При отставании |
|---|---|---|---|---|---|
| `statistics.impression.aggregate.v1` | `impression` | Дедуп, запись в ClickHouse, минутные агрегаты | до 64 | ≤ 60 с | Алерт, масштабирование (≤ партиций) |
| `statistics.click.aggregate.v1` | `click` | То же для кликов | до 16 | ≤ 60 с | Алерт |
| `billing.charge.v1` | `impression` | Расчёт расхода, запись `billing.charge`, ledger-батчи | до 64 | ≤ 60 с | P1-алерт; списание не блокирует выдачу |
| `reporting.materialize.v1` | `impression`, `click`, `spend` | Материализация витрин `mart.*` | до 64 | ≤ 5 мин | Не инцидент, если ≤ 15 мин |
| `analytics.ingest.v1` | `impression`, `click`, `bid.decided` (сэмпл) | Долгая история в S3 и витрины | до 32 | ≤ 15 мин | Не инцидент |
| `bidding.config.v1` | `campaign.changed`, `campaign.snapshot.ready` | Применение конфигурации в Bid Edge | до 32 | ≤ 30 с | Деградация L1: снапшот не старше 15 мин |
| `dsp.sync.v1` | `dsp.sync` | Синхронизация состояния с DSP | до 8 | ≤ 1 мин | Повтор с backoff |
| `audit.ledger.v1` | `audit.events` | Запись аудита | до 8 | ≤ 5 мин | Не критично |
| `replay.*` | Любой | Отдельная группа для replay, не влияет на прод | — | — | Ручной запуск |

### 6.2. Правила групп

1. **Имя группы: `<сервис>.<назначение>.v1`.** Версия в имени позволяет запустить новую логику параллельно без сброса offset.
2. **Потребителей ≤ партиций.** Иначе лишние простаивают.
3. **Cooperative-sticky assignor** и `group.instance.id` (static membership) — меньше ребалансов при деплое.
4. **Коммит offset — после обработки.** At-least-once; повтор безопасен благодаря дедупу.
5. **Один топик — много групп, но одна группа — один логический потребитель.** Иначе двойная нагрузка и расхождения.
6. **Финансовую группу масштабируем с проверкой идемпотентности.** Увеличение числа потребителей меняет распределение и порядок, проверяем на staging.
7. **Replay — только отдельной группой.** Сбрасывать offset продовой группы нельзя (риск остановки и двойных списаний).

### 6.3. Почему у Statistics и Billing разные группы

Оба читают `impression`, но задачи разные. Statistics пишет факты/агрегаты (важна пропускная способность). Billing считает деньги (важны идемпотентность и порядок по кампании). Разные группы дают независимый лаг, масштабирование и сбой: отставание отчётности не задерживает списание, сбой биллинга не останавливает статистику. Это следствие принципа «один писатель на набор данных».

## 7. Гарантии доставки и идемпотентность

### 7.1. Настройки продюсера

| Параметр | Значение | Почему |
|---|---|---|
| `acks` | `all` | Подтверждение всеми ISR; с `acks=1` цель ≤ 0,01% потерь не держится |
| `enable.idempotence` | `true` | Защита от дублей при внутренних ретраях |
| `max.in.flight.requests.per.connection` | `5` | Совместимо с идемпотентностью и даёт пропускную способность |
| `compression.type` | `zstd` | Меньше диск и сеть |
| `linger.ms` | `5` (телеметрия), `0` (деньги) | Батчинг для телеметрии; деньги — без задержки |
| `delivery.timeout.ms` | `120000` | Верхняя граница повторов |
| `buffer.memory` | `64 МБ` на продюсера | Буфер на кратковременный отказ |

### 7.2. Настройки консьюмера

| Параметр | Значение | Почему |
|---|---|---|
| `enable.auto.commit` | `false` | Коммит только после успешной обработки |
| `isolation.level` | `read_committed` | Не читать отменённые транзакции |
| `max.poll.records` | `500` | Ограничение пачки, чтобы не превысить `max.poll.interval.ms` |
| `max.poll.interval.ms` | `300000` | Запас на обработку батча |
| `session.timeout.ms` | `45000` | Меньше ложных ребалансов при долгой обработке |
| `auto.offset.reset` | `earliest` (статистика), `none` (деньги) | Для денег лучше остановиться, чем молча начать с середины |

### 7.3. Семантика

**At-least-once + дедупликация = фактически однократная обработка.** Сквозного exactly-once между Kafka, PostgreSQL, ClickHouse и внешним партнёром нет, обещать его не будем.

| Механизм | Где применяется |
|---|---|
| Идемпотентный продюсер | Все продюсеры |
| Уникальный `event_id` | `impression`, `click` — дедуп в Statistics и Billing |
| `unique(campaign_id, window_start, window_end)` | `spend_batch` в Billing |
| `unique(topic, partition, offset)` | `consumed_offset` — защита от повторного списания при ребалансе |
| Outbox | `campaign.changed`, `spend`, `invoice.issued` — публикация в транзакции с БД |
| Транзакции Kafka | Только read-process-write внутри одного сервиса, не сквозь границы |
| DLQ | Сообщения, не обработанные после N попыток |

Сквозной exactly-once потребовал бы распределённой транзакции через все хранилища и партнёров — это сознательно отвергнуто в [ADR-001](../Task1/adr/ADR-001-architecture-evolution-strategy.md). Дедупликация и сверка дешевле и надёжнее.

### 7.4. Outbox

Схема: `outbox(id, aggregate_id, event_type, payload, created_at, published_at)`. Публикация — через Debezium (logical replication) или relay-процесс с `SELECT ... FOR UPDATE SKIP LOCKED`.

Правила:

1. Событие пишется в той же транзакции, что и изменение домена.
2. Публикация идемпотентна по `id`.
3. `published_at` ставится после подтверждения `acks=all`.
4. Зависшие записи (не опубликованы > 5 мин) дают алерт и автоповтор.
5. Outbox — не вечная очередь: retention 7 дней, дальше архив.

### 7.5. DLQ

| Причина | Топик | Действие |
|---|---|---|
| Ошибка схемы (несовместимое сообщение) | `*.dlq.v1` | Разбор, исправление продюсера, replay |
| Ошибка бизнес-логики (нет кампании, отрицательная цена) | `*.dlq.v1` | Разбор, ручное решение |
| Исчерпаны повторы (5 с backoff до 30 с) | `*.dlq.v1` | Алерт; финансовые — P1 |
| Временная недоступность БД | **Не DLQ** | Повтор с backoff, пауза партиции |

DLQ — не свалка: у каждого сообщения есть причина, время и trace id. Разбор обязателен.

## 8. Replay и восстановление

### 8.1. Когда нужен replay

| Ситуация | Что переигрываем | Куда | Ограничение |
|---|---|---|---|
| Ошибка в агрегации Statistics | `impression`, `click` за окно | Новая таблица или партиция ClickHouse | Только в рамках retention (7 дней) |
| Ошибка в расчёте списания | `impression` за окно | Shadow-таблица и сверка с ledger | Не писать напрямую в ledger: только через проверенную агрегацию |
| Восстановление ClickHouse | Все доступные события | Новая реплика или партиция | 7 дней из Kafka и S3 Parquet |
| Новая витрина | Исторические события | `mart.*` | S3 Parquet за пределами retention |
| Проверка гипотезы | Сэмпл | Отдельный стенд | Не в прод-группе |

### 8.2. Процедура

1. Создать отдельную группу `replay.<purpose>.<date>`.
2. Сбросить offset на `timestamp` начала окна (`kafka-consumer-groups --reset-offsets --to-datetime`).
3. Читать с ограничением скорости: не больше 30% пропускной способности прод-группы.
4. Писать в теневую таблицу или топик с суффиксом `_replay`.
5. Сверить `count`/`sum` с прод-данными; расхождение объяснить до переключения.
6. Переключить чтение на восстановленные данные; старые оставить на 7 дней для отката.

**Запрещено:** сбрасывать offset продовой группы, переигрывать финансовые события напрямую в ledger, запускать replay без ограничения скорости.

## 9. Мультирегион

| Топик | Режим | Инструмент | RPO | Комментарий |
|---|---|---|---|---|
| `impression`, `click` | Active-active по регионам | MirrorMaker 2 и дедуп по `event_id` | ≤ 5 мин | Дубли допустимы: дедупликация в потребителях |
| `bid.decided`, `no_bid` | Active-passive | MM2 | ≤ 5 мин | Телеметрия, потеря допустима |
| `campaign.changed` | Active-passive (из региона-писателя) | MM2, `compact` | ≤ 30 с | Второй регион только читает |
| `spend`, `billing.charge` | Active-passive | MM2 с `sync`-подтверждением | ≤ 30 с | Писатель — только регион A; split-brain запрещён |
| DLQ | Не реплицируется | — | — | Разбор в регионе-источнике |

**Правила:**

1. **Никаких циклов.** MM2 с `replication.policy` исключает реплицированные топики и использует префикс источника.
2. **Один писатель на финансовые топики.** Регион B не производит `spend`, даже если принимает трафик.
3. **Offset-трансляция.** При failover потребители начинают с `earliest` непрочитанного или с транслированного offset; проверка на дубли обязательна.
4. **Проверка на учениях.** Раз в квартал — переключение региона и сверка (см. [scaling.md §8.4](scaling.md#84-учения)).

## 10. Эксплуатация

### 10.1. Мониторинг

| Метрика | Порог | Алерт |
|---|---|---|
| Consumer lag | > 60 с (Statistics, Billing), > 5 мин (Reporting) | P1/P2 |
| Under-replicated partitions | > 0 в течение 5 мин | P1 |
| Offline partitions | > 0 | P1 |
| ISR shrink rate | Рост | P2 |
| Produce latency P99 | > 50 мс | P2 |
| Request rate / network | > 70 % ёмкости | P2 |
| Disk usage | > 70 % | P2 |
| DLQ rate | > 0,01 % от потока | P1 (деньги), P2 (остальное) |
| Rebalance rate | > 1 в час на группу | P2 |
| Schema Registry errors | > 0 | P1 |

### 10.2. Безопасность

| Требование | Реализация |
|---|---|
| Транспорт | TLS 1.3 между клиентами и брокерами, между брокерами |
| Аутентификация | mTLS (SPIFFE в финале) или SASL/SCRAM-SHA-512; без анонимного доступа |
| Авторизация | ACL на топик и группу: продюсер пишет только в свои топики, консьюмер читает только свои |
| Квоты | `producer_byte_rate` / `consumer_byte_rate` на клиента; один сервис не выедает кластер |
| Шифрование диска | Обязательно |
| PII | Только хеши; raw IP не публикуется; consent-флаги обязательны |
| Аудит | Изменения ACL и топиков идут в audit-топик и Git |
| Schema Registry | Отдельный ACL: публикация схем — только CI-учётка |

### 10.3. Runbook (кратко)

| Симптом | Первое действие |
|---|---|
| Лаг растёт, потребитель жив | Проверить число потребителей против партиций, масштабировать до числа партиций |
| Лаг растёт, потребитель падает | Смотреть DLQ и логи; откатить релиз |
| Under-replicated партиции | Проверить брокер и сеть; не отключать `minISR` |
| Диск > 80 % | Включить tiered storage, снизить retention телеметрии |
| Ошибка схемы | Проверить совместимость в Registry, откатить продюсера, replay из DLQ |
| Ребаланс-шторм | Static membership, увеличить `session.timeout.ms`, проверить GC |

## 11. Что не взяли

| Вариант | Почему |
|---|---|
| JSON без Schema Registry | Нет контроля эволюции; ошибка поля всплывает в проде, а не в CI |
| Exactly-once «сквозь всё» | Невозможно между Kafka/PostgreSQL/ClickHouse/партнёром; ложная гарантия |
| Один топик на все события | Разные retention, ключи и потребители; смешение телеметрии и денег недопустимо |
| Retention 30–90 дней на все топики | SSD растёт линейно; историю хранят S3 и ClickHouse |
| Автоматический replay при ошибке | Маскирует дефект и создаёт двойные списания |
| Одна группа потребителей на всё | Сбой отчётности останавливает деньги; лаг одного блокирует других |
| Партиционирование по `user_id` | Неравномерность, нет локальности по кампании; порядок по пользователю не нужен |
| RF=5 | RF=3 достаточно; больше сеть/диск без выигрыша для SLA 99,9 % |
| Транзакции для сквозной обработки | Распределённая транзакция, отвергнута в ADR-001 |
| Kafka как единственное хранилище отчётов | Нет индексов и агрегатов; аналитика в ClickHouse |
