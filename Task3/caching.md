# Кеширование в AdScale

**Статус:** рабочая версия  
**Схема:** [diagrams/Caching_Layers.puml](diagrams/Caching_Layers.puml)

## 1. Зачем кеш и где тут риски

Сейчас кеша нет: кампании и ставки читаются из PostgreSQL на каждый запрос (~30k чтений/с на пике). Кеш снимет эту нагрузку, но может и навредить — закешированный «на века» бюджет даёт перерасход, устаревший конфиг — показ остановленной кампании.

## 2. Что кешируем и что нет

### 2.1. Кешируем

| Данные | Зачем | Требование к свежести |
|---|---|---|
| Конфигурация кампаний и таргетинга | Читается на каждый bid, меняется редко | ≤ 30 с P95 (финал 10 с) |
| Политики ценообразования (pricing) | Версионируются целиком, в каждом аукционе | До следующего релиза конфига |
| Креативы (`adm`) | Предсобранная разметка, одинакова для всех | До изменения креатива (версия в ключе) |
| Индекс кандидатов | Отбор по placement требует обратного индекса | До версии снапшота |
| Счётчики pacing и frequency cap | Атомарные операции на каждый аукцион | Точность в пределах окна |
| Резерв бюджета | Проверка/резерв за ~4 мс | Немедленно, в пределах аукциона |
| Kill switch | Должен примениться за секунды | ≤ 5 с, приоритетный канал |
| Квоты партнёров | Проверка на каждом запросе gateway | Окно 1 минута |
| API-ключи и JWKS | Проверка подписи на каждом запросе | ≤ 60 с, отзыв — принудительно |
| Отчёты и списки в кабинете | Тяжёлые запросы, небольшая задержка ок | ≤ 5 мин, пометка «на момент» |
| Баланс в кабинете | Часто смотрят, меняется редко | ≤ 30 с, только для отображения |
| Креативы и статика (CDN) | Байты, неизменяемые URL | Долго (immutable) |
| Витрины аналитики | Тяжёлые агрегаты | До следующей материализации |

### 2.2. Не кешируем

| Данные | Почему |
|---|---|
| **Решение аукциона** (кто выиграл) | Зависит от пользователя, контекста, бюджета, конкурентов — кеш решения = ставка по устаревшим условиям |
| **Баланс счёта как источник истины** | Кеш не может разрешать списание; истина — ledger, кеш — только отображение |
| **Финансовый ledger** | Append-only журнал; промежуточные суммы скрывают расхождения |
| **Права доступа и роли** | Инвалидация прав не должна зависеть от TTL; проверка по токену/БД |
| **PII в открытом виде** | Лишняя поверхность утечки; допустим только хеш |
| **Результаты сверки** | Устаревший отчёт о расхождении хуже отсутствия |

Важно различать два «бюджета»:
- **Оперативное состояние резерва** (`bid:camp:*` в Redis) — сколько зарезервировано/потрачено в окне, рабочее для аукциона.
- **Финансовая истина** (`ledger_entry` в PostgreSQL) — сколько реально списано, периодически сверяется с резервом.

Redis здесь ведёт рабочий счётчик, а не кеширует баланс. При потере его пересчитывают из ledger.

## 3. Слои и размещение

### 3.1. Слои

| Слой | Где | Что | Доступ |
|---|---|---|---|
| **L0. CDN** | Edge | Креативы, статика кабинета | 5–30 мс |
| **L1. In-process** | Память пода | Индекс кампаний, `adm`, политики, локальный fallback | 50–200 нс |
| **L2. Redis** | Кластер в регионе | Снапшоты, конфиг для BFF, счётчики, квоты, отчёты | 0,3–1 мс |
| **L3. Хранилище** | PostgreSQL / ClickHouse / S3 | Источник истины и архив | 1–50 мс |

L1 — основной для аукциона: 18k RPS читают индекс из памяти, а не из Redis. L2 нужен там, где состояние общее для подов (счётчики, резервы, квоты) или данные велики для каждого пода (снапшоты, отчёты). Класть в Redis то, что уже в L1 каждого пода — лишний сетевой хоп.

### 3.2. Кластеры Redis

Три кластера, независимых. Один «на всё» не подходит.

| Кластер | Назначение | Топология | Политика памяти | Почему отдельно |
|---|---|---|---|---|
| `redis-bid` | Pacing, frequency cap, резервы, kill switch | 6 шардов × (primary + replica), 3 AZ | `noeviction` | Вытеснение счётчика = потеря контроля бюджета; изоляция от кеша отчётов |
| `redis-rl` | Квоты партнёров на gateway | 3 шарда × (primary + replica), 3 AZ | `noeviction` | Лимиты нельзя вытеснять |
| `redis-cache` | Конфиг для BFF, отчёты, списки, JWKS | 3 шарда × (primary + replica), 3 AZ | `allkeys-lru` | Кеш можно вытеснять, LRU — норма |
| CDN | Креативы и статика | Внешний edge | — | Не Redis; раздача байтов |

**Правила:** кластеры в том же регионе/AZ, что и потребители; `prefer-local-az`; TLS и ACL по префиксам; никаких `KEYS/SCAN` в hot path — только операции по известным ключам.

### 3.3. Почему не один кластер

Один Redis = шумный сосед. Всплеск отчётов может вытеснить счётчики аукциона или занять память. Три кластера дороже в деньгах, но дешевле, чем проблемы с бюджетом и деградация из‑за отчёта.

## 4. Ключи, TTL и инвалидация

### 4.1. Таблица ключей

| Ключ | Содержимое | TTL | Инвалидация | Если TTL истёк / кеш потерян |
|---|---|---|---|---|
| `bid:camp:{campaign_id}` | `spent_micros`, `reserved_micros`, `pacing_tokens`, `version` | 48 ч | Write-through при каждом резерве/списании; сверка с ledger раз в минуту | Пересчёт из ledger (watermark); консервативный pacing на время пересчёта |
| `bid:pace:{campaign_id}:{minute}` | Счётчик показов за минуту | 2 ч | Инкремент при показе | Минутное окно начинается заново, аукцион не блокируется |
| `bid:cap:{campaign_id}:{scope}:{key}:{window}` | Счётчик частоты | `window` + 10% | Инкремент; естественное истечение | Возможен лишний показ в пределах окна |
| `bid:kill:{scope}` | Флаг остановки (партнёр/кампания/глобально) | 5 с | Приоритетный pub/sub (не Kafka); продление активного флага | Флаг исчезнет — поэтому TTL короткий и с постоянным продлением |
| `cfg:campaign:{campaign_id}` | Сериализованная конфигурация | 10 мин | Событие `campaign.changed.v1` (по версии) | Чтение из снапшота/БД, рост задержки BFF допустим |
| `cfg:snapshot:{version}` | Полный снапшот (immutable) | 24 ч | Не инвалидируется (версия в ключе) | Перегенерация из Campaign; старые чистит GC |
| `cfg:release:{release_id}` | Набор политик релиза (immutable) | 24 ч | Не инвалидируется | Загрузка из PostgreSQL Bidding |
| `cfg:etag:{version}` | ETag снапшота для условных запросов | 24 ч | Не инвалидируется | Повторная загрузка |
| `rl:{partner_id}:{minute}` | Счётчик квоты | 2 мин | Естественное истечение; `EVALSHA` | Локальный лимит gateway 70% (fail-open) |
| `gw:key:{hash(api_key)}` | `partner_id`, права, срок | 60 с | Принудительная инвалидация pub/sub | Проверка в БД ключей; рост задержки |
| `gw:jwks` | Публичные ключи | 5 мин | По `kid`, принудительно | Загрузка JWKS; при недоступности — отказ админ-API |
| `bff:campaigns:{advertiser_id}:{page}` | Список кампаний | 60 с | Событие изменения кампании | Чтение из Campaign |
| `bff:report:{report_hash}` | Готовый отчёт | 5 мин | Новая материализация витрины | Пересчёт или чтение ClickHouse |
| `bff:balance:{account_id}` | Баланс «на момент» | 30 с | TTL; пометка временем | Чтение реплики Billing |
| `ana:report:{report_id}` | Тяжёлый отчёт | 15 мин | Новая материализация или ручной purge | Выполнение запроса в ClickHouse |
| CDN URL с хешем | Креатив, статика | 30–365 дней | Не инвалидируется (новый хеш = новый URL) | Обращение к origin S3 |

TTL для `bid:*` согласованы с [bidding-service.md §4.3](../Task2/bidding-service.md), для `rl:*` — с [api-gateway.md §7.2](../Task2/api-gateway.md).

### 4.2. Почему такие TTL

TTL — страховка от пропущенной инвалидации, а не основной механизм свежести. Для конфига актуальность подтверждается событием и проверкой версии (раз в 30 с); TTL 10 мин — верхняя граница жизни записи, если что-то пошло не так.

| Данные | Допустимое устаревание | TTL | Комментарий |
|---|---|---|---|
| Конфигурация кампании | 30 с (финал 10 с) | 10 мин | Верхняя граница при потере событий; дальше — принудительная догрузка |
| Kill switch | 5 с | 5 с | Остановка показа не может ждать |
| Квота партнёра | 1 мин | 2 мин | Окно + запас на границу |
| Баланс в кабинете | 30 с | 30 с | Только отображение («на момент») |
| Отчёт | 5 мин | 5 мин | Совпадает с материализацией |
| Снапшот | Версия неизменяема | 24 ч | Нужен для загрузки, старые чистит GC |

Чего не делаем: длинный TTL (часы/сутки) на конфиг «ради производительности» — тогда инвалидация перестаёт работать вовремя.

### 4.3. Стратегии инвалидации

| Тип данных | Механизм | Гарантия |
|---|---|---|
| Конфигурация кампании | **Event-driven**: `campaign.changed.v1` с монотонной `version` (применяем если `version > applied_version`) | Идемпотентно; пропуск события не откатывает назад |
| Конфигурация (страховка) | Периодическая проверка версии снапшота (ETag) раз в 30 с | Покрывает редкие потери/проснувшиеся поды |
| Политики и релизы | **Версия в ключе** (`cfg:release:{id}`) | Откат — переключение указателя, без удаления |
| Счётчики и резервы | **Write-through** (Lua) | Нет окна, когда резерв не учтён |
| Kill switch | Приоритетный pub/sub + TTL 5 с | Не зависит от лага Kafka |
| Квоты | Естественное истечение окна | Точность ±1% глобально |
| Ключи и JWKS | TTL + принудительная инвалидация по событию | Отзыв ≤ 60 с (аварийно быстрее) |
| Отчёты и списки | TTL и явный purge при материализации | Свежий отчёт после обновления витрины |
| CDN | Immutable URL с хешем | Инвалидация не нужна |

### 4.4. Почему инвалидация по версии

Конфиг инвалидируем событием с версией, а не только по таймеру: порядок сообщений не гарантирован (проверка `version > applied` защищает от отката), повторная доставка безопасна (at-least-once), откат — это новая версия (а не удаление ключа), а в ответах видна `X-Config-Version` для диагностики.

## 5. Прогрев кеша

### 5.1. Холодный старт пода Bidding

Под без индекса трафик не принимает:
1. `readiness = false` сразу при старте.
2. Загрузка последнего снапшота: из S3 (предпочтительно) или `GET /internal/v1/snapshots/{version}` с реплики Campaign (не с primary).
3. Проверка `checksum` и `version`; при расхождении — повтор и алерт.
4. Построение индекса: `byPlacement`, `byCampaign`, `creativeIndex`, обратные индексы (200–500 МБ, цель ≤ 20 с).
5. Подписка на `campaign.changed.v1` и догон событий с `version > snapshot.version`.
6. `readiness = true` только после `Health.serving = true` и совпадения checksum.

Цели: до readiness ≤ 20 с (P95), ≤ 40 с (P99); доля неуспешных прогревов ≤ 0,1%.

### 5.2. Деплой и автомасштабирование

| Ситуация | Что делаем |
|---|---|
| Rolling update | `maxSurge=1`, `maxUnavailable=0`: новый под прогревается, потом выводится старый |
| Одновременный старт N подов | Jitter 0–30 с, чтобы не устроить пик на S3/Campaign |
| Автомасштабирование в пик | Снапшот заранее прогрет на узле (DaemonSet/init-контейнер), не строим индекс «с нуля из БД» |
| Потеря Redis | Перезапуск подов не нужен: L1 живёт, счётчики восстанавливаются из ledger |
| Потеря пода | Новый прогревается по процедуре, трафик на остальных |

### 5.3. Прогрев Redis

| Что | Когда | Как |
|---|---|---|
| `cfg:snapshot:*` | При активации новой версии | Публикация в S3 и запись в Redis из Campaign (write-through), без primary |
| `cfg:campaign:*` | При изменении кампании | Событие `campaign.changed.v1` → инвалидация и опциональный предзагруз |
| `gw:key:*`, `gw:jwks` | Старт пода gateway / ротация | Загрузка из сервиса ключей; кеш локальный |
| `bff:report:*` | После материализации витрины (02:00–03:00) | Reporting прогревает топ-N отчётов перед утренним пиком |
| `bff:campaigns:*` | Перед рабочим пиком (05:30 локального времени) | Прогрев списков активных рекламодателей |
| `ana:report:*` | По запросу | Ленивый прогрев + кеш 15 мин; фоновый прогрев топ-20 |

Правила: прогрев не грузит primary (источник — S3/реплика/Redis); ограничен по скорости; идемпотентен; наблюдаем (`cache_warm_duration_seconds`, `cache_warm_failures_total`, `cache_ready_pods`); если снапшот не загрузился — под не становится ready.

### 5.4. После сбоя

- **Отказ Redis:** счётчики восстанавливаются из ledger Billing по watermark; временно `LOCAL_PACE` и консервативные ставки, доля трафика ≤ 10% (см. [interaction.md §7.5](../Task2/interaction.md)).
- **Отказ ClickHouse:** витрины не прогреваются, отчёты недоступны; `bff:report` отдаёт последние версии до истечения TTL.
- **Отказ региона:** новый регион прогревает L1 из реплики S3, Redis стартует пустым и наполняется по запросам, бюджет — консервативный pacing 1–2 минуты.

## 6. Согласованность, лавины, деградация

### 6.1. Защита от cache stampede

| Приём | Где | Что даёт |
|---|---|---|
| **Singleflight** | BFF, Reporting | Много запросов одного отчёта → один поход в ClickHouse |
| **Распределённая блокировка** `SET NX PX 500` | Redis, пересчёт снапшота | Пересобирает один, остальные ждут |
| **Jitter в TTL** | Все ключи | Истечение не синхронно |
| **Stale-while-revalidate** | `bff:*`, `ana:*` | Отдаём устаревшее, обновляем в фоне |
| **Probabilistic early expiration** | `cfg:*` | Обновление до истечения |
| **Ограничение конкурентности** | Клиент Redis, BFF | При перегрузке — быстрый деградированный ответ |

### 6.2. Согласованность

| Вопрос | Ответ |
|---|---|
| Можно ли отдать устаревший конфиг? | Да, но не старше 15 мин; дальше — принудительная догрузка, затем дефолтные политики |
| Можно ли отдать устаревший баланс? | Только для отображения, с пометкой «на момент». Для списания — primary и ledger |
| Можно ли отдать устаревший отчёт? | Да, если указано время материализации |
| Что важнее: свежесть или доступность? | Для аукциона — доступность с консервативным поведением; для денег — корректность, даже ценой задержки |
| Как проверить «кеш не истина»? | Учение: полное удаление Redis в staging не меняет финансовый результат и не останавливает выдачу |

### 6.3. Матрица деградации

| Отказ | Bid path | Кабинет | Деньги | Поведение |
|---|---|---|---|---|
| `redis-bid` | `LOCAL_PACE`, консервативные ставки, ≤ 10% трафика | Не затронут | Резервы не пишутся, списание по факту | Восстановление из ledger |
| `redis-rl` | Локальные лимиты gateway 70% | Не затронут | Не затронуты | Возможен небольшой перерасход квоты |
| `redis-cache` | Не затронут (L1) | Отчёты медленнее, списки из БД | Не затронуты | Деградация малозаметна |
| L1 не прогрелся | Под не получает трафик | — | — | Меньше ёмкости, но ответы корректны |
| CDN | Креативы с origin, рост задержки | Статика медленнее | Не затронуты | Origin S3 выдержит ограниченное время |
| ClickHouse Analytics | Не затронут | Отчёты недоступны | Не затронуты | Last-known report из кеша до TTL |

Правило: отказ кеша не должен давать `5xx` на bid path. Деградация — `204`, консервативная ставка или ответ из L1.

### 6.4. Безопасность кеша

| Требование | Реализация |
|---|---|
| Изоляция | Отдельные кластеры и ACL; сервис видит только свой префикс |
| Шифрование | TLS в транзите, шифрование диска; в ключах — только идентификаторы, не PII |
| Ключи | `api_key` хранится как хеш (`sha256`) |
| Доступ | Redis в приватной сети, без публичного endpoint |
| Аудит | Изменения конфигурации кеша (TTL, лимиты) — через ревью и версионирование |
| Отравление кеша | Запись только из доверенных сервисов; ключи с версией; проверка схемы при десериализации |

| Метрика | Цель | Алерт |

| Hit ratio L1 (Bidding) | ≥ 99% (индекс в памяти) | < 95% 5 мин |
| Hit ratio L2 `cfg:*` | ≥ 90% | < 80% 10 мин |
| Hit ratio `bff:report` | ≥ 70% | < 50% 15 мин |
| Redis latency P99 (`redis-bid`) | ≤ 1 мс | > 5 мс 5 мин |
| Redis latency P99 (`redis-cache`) | ≤ 2 мс | > 10 мс 10 мин |

| Время прогрева пода | ≤ 20 с P95 | > 40 с три раза подряд |

## 8. Что не взяли

| Вариант | Почему |
|---|---|
| Один Redis Cluster на всё | Шумный сосед, общий отказ |
| Кешировать решение аукциона | Ставка по устаревшим условиям, перерасход |
| Кешировать баланс как источник истины | Нельзя гарантировать корректность списаний |
| TTL-only инвалидация конфига | Показ остановленной кампании до истечения TTL |
| Бессрочный кеш | Изменения становятся невидимыми, нет отката |
| Redis как primary store | Нет ACID/аудита/надёжности |
| Локальный кеш без версии | Поды расходятся, воспроизведение аукциона невозможно |
| `KEYS`/полный скан в hot path | O(N), блокирует Redis |
| Репликация кеша между регионами | WAN убивает hot path |
| Прогрев из primary | Пик чтения конкурирует с записью |
| Кеширование PII | Лишняя поверхность утечки |
