# Масштабирование хранилищ AdScale

**Статус:** рабочая версия
**Горизонт:** 3 мес — 18 000 RPS, 12 мес — 50 000 RPS
**Схемы:** [diagrams/Scaling_Sharding_Map.puml](diagrams/Scaling_Sharding_Map.puml), [diagrams/C4_Deployment_DataTopology.puml](diagrams/C4_Deployment_DataTopology.puml)

## 1. С чего начинаем

Сейчас 15 000 RPS дают примерно 45–90 тыс. операций/с на один PostgreSQL. На 18 000 RPS это уже ~54–108 тыс., на 50 000 — ~150–300 тыс. Реплик, нормального кеша и партиционирования по сути нет.

Что нужно понять:

1. где хватает репликации master–slave, а где она не спасает;
2. что и по какому ключу шардировать, и при каких порогах;
3. нужны ли аналитике read replicas и какие именно;
4. где CQRS реально помогает, а где только усложняет.

Подход простой: сначала убрать лишнюю нагрузку (кеш, разделение по типам), потом реплицировать, и только в конце шардировать. Шардирование дорого в эксплуатации, поэтому откладываем до явной необходимости.

## 2. Модель нагрузки

### 2.1. Профили по хранилищам

| Хранилище | Запись (3 мес) | Запись (12 мес) | Чтение (3 мес) | Чтение (12 мес) | Характер |
|---|---|---|---|---|---|
| PostgreSQL Bidding | ~10 оп/с | ~20 оп/с | Админка, старт подов | То же | Малый объём, транзакции |
| PostgreSQL Campaign | 20–200 RPS | 50–500 RPS | 500–2 000 RPS (BFF, снапшоты) | 2 000–6 000 RPS | OLTP, чтение преобладает |
| PostgreSQL Billing | ~30–40 батчей/с (~2–3 млн строк/сут) | ~80 батчей/с (~6 млн строк/сут) | Отчёты/сверка, минуты | То же | Строгая согласованность |
| ClickHouse Statistics | 12 000 событий/с (batch) | ~33 000 событий/с | 10–50 запросов/с | 50–200 запросов/с | Append-only и агрегаты |
| ClickHouse Analytics | — (read-only) | — | 5–50 тяжёлых запросов | 20–200 тяжёлых запросов | OLAP, большие окна |
| Redis Bidding | ~36 000 оп/с | ~100 000 оп/с | То же (Lua, 2 RTT) | То же | In-memory, атомарные операции |
| Kafka | 30 000 msg/с | ~85 000 msg/с | Потребители в своих группах | То же | Лог, последовательная запись |

Прикидка: 18 000 RPS × 86 400 с ≈ 1,55 млрд bid request/сут, до показа доходит ~12 000/с (~1,04 млрд строк/сут). В финале 50 000 RPS → ~4,3 млрд запросов и ~2,85 млрд показов. Сходится с [../Task2/interaction.md §5.3](../Task2/interaction.md#53-модель-событий).

### 2.2. Где реально болит

| Узкое место AS-IS | Что помогает | Что не поможет |
|---|---|---|
| Чтение кампаний/ставок на каждый запрос | Кеш L1/L2 и снапшот в памяти | Реплика БД (чтение всё равно в hot path) |
| Запись показов в ответе пользователю | Kafka и асинхронный учёт | Реплика (пишем в primary) |
| Тяжёлые отчёты на рабочей БД | Отдельный ClickHouse read-контур | Реплика PostgreSQL (скан остаётся построчным) |
| 45–90 тыс. оп/с на одном сервере | Разделение по сервисам, кеш, батчинг | Только вертикальное масштабирование (потолок) |

Отсюда порядок: кеш → разделение хранилищ → репликация → шардирование. Кеш — в [caching.md](caching.md).

## 3. Репликация

### 3.1. Сводная матрица

| Хранилище | Режим | Реплики | Гарантия | Failover | Зачем |
|---|---|---|---|---|---|
| PostgreSQL Bidding | Sync (`remote_write`) в другую AZ | 1 sync + 1 async | RPO 0 при отказе AZ | Patroni, авто 30–60 с | Конфиг/аудит терять нельзя; запись маленькая |
| PostgreSQL Campaign | Sync в другую AZ | 1 sync + 2 async read | RPO 0 | Patroni | Источник истины; async обслуживают чтение |
| PostgreSQL Billing | Sync в AZ **и** в DR | 1 sync AZ + 1 sync DR + 1 async | **RPO 0** | Patroni + кворум etcd | Деньги; запись батчами, WAN-задержка терпима |
| ClickHouse Statistics | Async (`ReplicatedMergeTree`) | 2 на шард | At-least-once из Kafka + дедуп | Авто на уровне таблицы | Источник — Kafka/S3, реплику можно восстановить |
| ClickHouse Analytics | Async | 2 на шард | Eventual | Авто | Read-контур, отставание в минуты ок |
| Redis Bidding / RL / Cache | Async (реплика на шард) | 1 на шард | Потеря счётчиков до ~30 с допустима | Sentinel / Redis Cluster failover | Не источник истины, восстанавливаем из ledger |
| Kafka | RF=3, `min.insync.replicas=2` | 3 | RPO 0 в пределах региона | Controller election | Основа асинхронного контура |

### 3.2. PostgreSQL: параметры и поведение

**Топология.** Patroni, etcd (3 узла), HAProxy и PgBouncer. Три AZ, sync-реплика в другой AZ, async для чтения. У Billing дополнительно sync-реплика в регионе DR.

| Параметр | Bidding / Campaign | Billing | Почему |
|---|---|---|---|---|
| `synchronous_commit` | `remote_write` | `on` | Для конфига достаточно записи WAL на реплику; для денег нужно подтверждение применения |
| `synchronous_standby_names` | `ANY 1 (az2, az3)` | `FIRST 2 (az2, region_b)` | Billing требует кворум «локальная AZ + DR» |
| `max_connections` | 200 | 200 | Приложение ходит через PgBouncer |
| `wal_level` | `logical` | `logical` | Outbox через Debezium (logical replication) |
| `hot_standby_feedback` | `on` | `on` | Меньше конфликтов на репликах чтения |
| `statement_timeout` | 5 с | 30 с | Долгий запрос не должен держать соединение |

**Пулы соединений.** Перед каждым кластером PgBouncer (`transaction`). При 18k RPS и ~5 мс удержания это ~90 одновременных соединений, а не тысячи. Пул на сервис 20–40, очередь с таймаутом 200 мс и быстрым отказом.

**Деградация гарантии.** Если у Billing sync-реплика в DR недоступна дольше 30 с, Patroni переводит кластер в `ANY 1 (az2, region_b)` и пишет событие в аудит. Если недоступны обе реплики — `synchronous_commit=local` с алертом P1. Доступность важнее, но факт снижения RPO фиксируем.

### 3.3. ClickHouse

- `ReplicatedMergeTree`, координация через ZooKeeper/Keeper (3 узла). Реплики в разных AZ.
- Запись в одну реплику, вторая догоняет асинхронно. `insert_quorum=2` — только там, где важна немедленная видимость после записи (`billing.charge`), но не для `stats.*` (источник — Kafka).
- Чтение через `Distributed` (`load_balancing=in_order`, `prefer_localhost_replica=0`) уходит на менее занятую реплику.
- Отставание по `ReplicasMaxAbsoluteDelay`. Алерт: >60 с для `stats.impression_minute`, >5 мин для сырых событий.

### 3.4. Redis

- Redis Cluster: 16 384 слота, шардирование по hash tag. Каждый шард — primary и replica в другой AZ.
- `WAIT 1` — только для резерва бюджета (не чаще раза на аукцион). Остальное реплицируется асинхронно.
- Реплика нужна для быстрого failover, не для чтения (читаем с primary). Promotion секунды, холодный пересчёт — минуты.
- Кластеры разделены по назначению (`redis-bid`, `redis-rl`, `redis-cache`), чтобы проблемы одного не задевали остальных (см. [caching.md](caching.md)).

### 3.5. Kafka

Подробно в [event-streaming.md](event-streaming.md): RF=3, `min.insync.replicas=2`, `acks=all`, `unclean.leader.election=false`. Главное: пока событие в Kafka, его можно переиграть даже при потере ClickHouse.

## 4. Шардирование

### 4.1. Решение по хранилищам

| Хранилище | Шардируем? | Ключ | Когда | Почему |
|---|---|---|---|---|
| PostgreSQL Bidding | **Нет** | — (в будущем `advertiser_id`) | Не планируется | Десятки тысяч кампаний, запись — единицы оп/с |
| PostgreSQL Campaign | **Нет на 12 мес** | `advertiser_id`, если понадобится | CPU primary > 80% или запись > 500 RPS | < 1 ТБ; чтение снимают реплики и кеш |
| PostgreSQL Billing | **Нет** | `advertiser_id` — крайняя мера | Горячий ledger > 1 ТБ или > 20k tx/с | Сверки/инварианты баланса требуют единого представления |
| ClickHouse Statistics | **Да** | `cityHash64(campaign_id)` | Сразу: 4 шарда (3 мес), 8 (12 мес) | 1–3 млрд строк/сут; равномерность + локальность агрегатов |
| ClickHouse Analytics | **Да** | `cityHash64(campaign_id)` | 2 шарда (3 мес), 4 (12 мес) | Параллелизм тяжёлых запросов |
| Redis Bidding | **Да** | `{campaign_id}` (hash tag) | 6 шардов (3 мес), 12 (12 мес) | 36–100k оп/с; один узел не тянет |
| Redis Cache | **Да** | Пространство ключей (`cfg:`, `bff:`) | 3 шарда | Изоляция + ёмкость |
| Kafka | **Да (партиции)** | `campaign_id` (события), `auction_id` (телеметрия) | 64 (3 мес), 128 (12 мес) для `impression` | Параллелизм потребителей и равномерность |

### 4.2. Почему именно эти ключи

**ClickHouse: `campaign_id`, не `advertiser_id` и не `event_id`.** `event_id` равномерный, но ломает локальность — агрегат по кампании придётся собирать со всех шардов. `advertiser_id` удобен для отчётов, но крупный рекламодатель может перекосить шард. `campaign_id` обычно распределяет лучше, а отчёт по рекламодателю читает ограниченный набор шардов (его кампании). На 4–8 шардах fan-out терпимый.

**Redis: `{campaign_id}` (hash tag).** Ключи одной кампании (`bid:camp`, `bid:pace`, `bid:cap`) должны быть в одном слоте для атомарной Lua-операции. Минус — риск горячего шарда (см. §4.5).

**Kafka: `campaign_id`.** Порядок в пределах кампании полезен для pacing/дедупа. Для `bid.decided` — `auction_id` (порядок не важен, важнее равномерность).

**PostgreSQL: партиции по времени, не шардирование.** В Billing/аудите это закрывает основное: партиции по месяцам, старые не греют hot-запросы, архив отцепляется, autovacuum локальнее.

### 4.3. Как шардировать без простоя

1. **Подготовка.** Новый шард поднят, запись ещё не принимает.
2. **Двойная запись.** Пишем в старый и новый, идемпотентно по естественному ключу.
3. **Backfill.** Копируем батчами (10–50k строк) с лимитом RPS, прогресс в метрике.
4. **Сверка.** `count`/`sum` по диапазонам ключей совпадают.
5. **Переключение чтения.** Читатели на новой топологии, старая — тёплый резерв.
6. **Выключаем двойную запись** после 24–72 ч стабильности.

ClickHouse: `INSERT INTO ... SELECT` по диапазонам `cityHash64(campaign_id) % N` (на время — ограничить merges, после — `OPTIMIZE`). Redis: reshard/`CLUSTER SETSLOT`, клиент обрабатывает `MOVED`.

### 4.4. Решардинг: когда и как

| Триггер | Порог | Действие |
|---|---|---|
| ClickHouse: CPU шарда | > 70% 30 мин на пике | Добавить шард, backfill |
| ClickHouse: диск | > 70% | Добавить шард или tiered storage в S3 |
| Redis: память | > 70% `maxmemory` | Добавить шард; сначала TTL/hot keys |
| Redis: CPU шарда | > 65% | Разделить горячую кампанию по под-ключам или добавить шард |
| Kafka: диск | > 70% | Добавить брокер, перераспределить партиции |
| PostgreSQL Billing | > 1 ТБ горячих данных | Отцепить старые партиции в S3/ClickHouse |
| PostgreSQL Campaign | > 80% CPU после добавления реплик | Рассмотреть Citus по `advertiser_id` |

### 4.5. Горячие ключи и перекосы

| Риск | Причина | Что делаем |
|---|---|---|
| Горячая партиция Kafka | Крупная кампания даёт заметную долю | 64–128 партиций; для телеметрии ключ `auction_id` |
| Горячий шард Redis | Hash tag `{campaign_id}` фиксирует ключи кампании | Мониторинг hot key; для гигантов — `{campaign_id}:b{N}` + агрегация; лимиты |
| Перекос ClickHouse | Аномальный объём у рекламодателя | Шард по `campaign_id`, контроль топ-100; при необходимости выделенный шард |
| Горячая партиция по времени | Вся запись в «сегодня» | Для append-only норма, узкое место — диск |
| Разрастание frequency cap | Много пар «кампания, пользователь» | TTL = окно+10%; cap только где включён; для крупных — count-min sketch (±1 показ) |

## 5. Read replicas и маршрутизация чтений

### 5.1. Какие чтения куда идут

| Сервис | Чтение | Источник | Допустимое отставание | Read-your-writes |
|---|---|---|---|---|
| Bidding | Конфигурация при старте | Снапшот из S3 или реплика Campaign | ≤ 30 с P95 | Проверка `version` и checksum |
| Bidding | Админ-просмотр состояния | Read replica PostgreSQL Bidding | ≤ 5 с | Не критично |
| Campaign | Снапшот для Bidding | Read replica | ≤ 5 с | Версия в ответе; ожидание `version >= N` |
| Campaign | Список кампаний в кабинете | Read replica через BFF | ≤ 5 с | После записи — по `version` с primary или ожидание |
| Billing | Баланс в кабинете | Read replica | ≤ 5 с, пометка «на момент» | Списание/вывод — только primary |
| Billing | Сверка и отчёты | ClickHouse `billing.charge` | ≤ 5 мин | — |
| Statistics | Дашборды | ClickHouse read replica | ≤ 60 с | — |
| Analytics | Отчёты | ClickHouse read-контур | ≤ 5 мин | — |

Правило: реплика — там, где допустимо отставание. Всё, что влияет на деньги или применение конфига, идёт с primary или проверяется по версии.

### 5.2. Нужны ли read replicas аналитике

Да, но не OLTP-реплики.

1. **Postgres read replica не решает задачу.** Агрегация миллиарда строк — всё равно построчный скан.
2. **Нужен отдельный ClickHouse read-контур** с асинхронной подачей данных.
3. **Реплики внутри контура обязательны:** параллелизм, отказоустойчивость, возможность увести дорогой отчёт на выделенную реплику.
4. **Кеш витрин реплики не заменяет:** нестандартные срезы/длинные окна всё равно сканируют.

Итого: аналитике — read replicas ClickHouse, материализованные витрины и S3 для истории. Read replicas PostgreSQL для аналитики не берём.

### 5.3. Балансировка чтения

- PgBouncer с пулами `primary` (запись/критичные чтения) и `replica` (обычные); выбор по типу операции.
- ClickHouse `Distributed` (`load_balancing=in_order`) + health-check; отставшая реплика исключается.
- Если все реплики недоступны — деградация до primary с ограничением конкурентности.

## 6. CQRS

### 6.1. Где используем

| Сервис | Command-модель | Query-модель | Проекция | Лаг | Зачем |
|---|---|---|---|---|---|
| **Bidding** | `config_release`, политики (PostgreSQL) | In-memory индекс и Redis (pacing, cap) | `campaign.changed.v1` + snapshot pull | ≤ 30 с (финал 10 с) | Запись конфига и чтение в аукционе (20 мс) — разные требования |
| **Statistics** | Приём событий (Kafka → ClickHouse) | `stats.*_minute`, `mart.*` | Materialized views/агрегация | ≤ 60 с | Сырые факты vs отчёты — разные профили |
| **Analytics** | Нет команд | Витрины `mart.*` и S3 | Reporting пишет витрины | ≤ 5 мин | Чистая read-модель |
| **Billing** | Ledger, баланс, счета (PostgreSQL) | `billing.charge`, `mart.finance_daily`, баланс с реплики | Outbox → Kafka → ClickHouse | ≤ 5 мин | Запись денег и чтение отчётов несовместимы; истина — ledger |
| **Campaign** | CRUD (PostgreSQL) | Снапшот для Bidding, списки для BFF | Outbox и версия | ≤ 5 с | Лёгкий CQRS для потребителей |

### 6.2. Где не используем

| Сервис | Почему нет |
|---|---|
| **Targeting** | Чтение/запись простые, точечные — проекция даст лаг без выигрыша |
| **API Gateway** | Доменных данных нет, только счётчики квот |
| **DSP Adapter** | Синхронизация/маппинг, не разделение чтения и записи |
| **Cabinet BFF** | Уже read-слой, своих моделей нет |

### 6.3. Правила

1. **CQRS ≠ event sourcing.** Состояние как поток событий храним только где это естественно (ledger). Проекция перестраивается из источника.
2. **Проекция идемпотентна и версионируема.** Монотонная версия, повтор события безопасен.
3. **Лаг — часть контракта.** Объявлен и покрыт алертом.
4. **Деньги не читаем из проекции.** Списание — из primary.
5. **Отставание не маскируем.** Помечаем (`X-Config-Version`, «данные на …»).

## 7. Ёмкость и триггеры

### 7.1. Целевая ёмкость

| Компонент | 3 месяца | 12 месяцев | Запас |
|---|---|---|---|---|
| PostgreSQL Bidding | 2 vCPU / 8 ГБ, 1 sync + 1 async | 4 vCPU / 16 ГБ | ~3× |
| PostgreSQL Campaign | 4 vCPU / 16 ГБ, 1 sync + 2 async | 8 vCPU / 32 ГБ, +1 async | ~3× |
| PostgreSQL Billing | 8 vCPU / 32 ГБ, sync AZ + sync DR | 16 vCPU / 64 ГБ | ~4× |
| ClickHouse Statistics | 4 шарда × 2 × (8 vCPU / 32 ГБ / 2 ТБ NVMe) | 8 шардов × 2 × (8 vCPU / 32 ГБ / 4 ТБ) | ~40% |
| ClickHouse Analytics | 2 шарда × 2 × (8 vCPU / 32 ГБ) | 4 шарда × 2 × (16 vCPU / 64 ГБ) | ~50% |
| Redis Bidding | 6 шардов × (4 vCPU / 16 ГБ) | 12 шардов × (4 vCPU / 32 ГБ) | ~40% |
| Kafka | 6 брокеров (2 на AZ), 3 ТБ NVMe | 9–12 брокеров, 6 ТБ | ~35% |
| S3 | 50 ТБ | 250 ТБ | — |

### 7.2. Триггеры и действия

| Метрика | Порог | Действие | Как |
|---|---|---|---|
| CPU primary PostgreSQL | > 60% на пике 15 мин | Добавить read-реплику, проверить планы | Алерт → решение дежурного |
| CPU primary PostgreSQL | > 80% | Вертикаль + кандидат на шардирование | Планово, ~2 недели |
| Replication lag | > 5 с (Campaign), > 30 с (Billing) | Исключить реплику из чтения, алерт | Авто |
| ClickHouse CPU | > 70% 30 мин | Добавить шард или реплику | Планово |
| ClickHouse `MaxPartCountForPartition` | > 150 | Ограничить вставки, ускорить merge | Авто |
| Redis memory | > 70% | Добавить шард, проверить TTL/hot keys | Планово |
| Redis latency P99 | > 5 мс | Проверить hot key/сеть; при подтверждении шардировать | Авто + разбор |
| Kafka disk | > 70% | Добавить брокер, перераспределить партиции | Планово |
| Kafka consumer lag | > 60 с (деньги/статистика), > 5 мин (аналитика) | Алерт, масштабировать потребителей ≤ партиций | Авто |
| Пул PgBouncer | Очередь > 20 запросов 1 мин | Увеличить пул или число реплик | Авто |
| Пул PgBouncer | Очередь > 20 запросов 1 мин | Увеличить пул или число реплик | Авто |

### 7.3. Авто vs вручную

- **Автоматически:** stateless-поды (HPA по RPS/P95), потребители Kafka (KEDA по лагу), read-реплики ClickHouse (полуавто).
- **Полуавто, с подтверждением:** новый шард ClickHouse/Redis, вертикаль PostgreSQL.
- **Вручную:** шардирование PostgreSQL, смена ключа партиционирования, переезд региона — план и окно.

## 8. Мультирегион

### 8.1. Топология

| Элемент | Регион A (active) | Регион B (DR / active для bid path) | Режим |
|---|---|---|---|
| Bid path (stateless) | Active | Active | GSLB по health/latency |
| PostgreSQL Bidding | Primary + sync AZ | Async-реплика | Ручное повышение (RTO ≤ 5 мин) |
| PostgreSQL Campaign | Primary + sync AZ | Async-реплика | Ручное повышение |
| PostgreSQL Billing | Primary + sync AZ | **Sync-реплика** | Авто-повышение по кворуму (RPO 0) |
| ClickHouse Statistics | Шарды и реплики | Реплики, питаются из MM2 | Async, RPO ≤ 5 мин |
| ClickHouse Analytics | Read-контур | Свой read-контур | Пересборка из S3 |
| Redis | Локальный кластер | Локальный кластер | Между регионами не реплицируем |
| Kafka | Primary | MirrorMaker 2 | RPO ≤ 5 мин (телеметрия), ≤ 30 с (`spend`) |
| S3 | Primary | Cross-Region Replication | Непрерывно |

### 8.2. Почему Redis не реплицируем между регионами

Счётчики pacing/frequency cap по сути региональны. WAN-задержка на каждую операцию резерва (30–70 мс) не влезает в бюджет 55 мс. У каждого региона свой кластер, глобальный бюджет контролируем через watermark из `spend.v1`, а при переключении счётчики пересчитываются из ledger с консервативным pacing на 1–2 минуты.

Компромисс: в момент failover возможен небольшой перерасход (~в пределах 0,1%), зато в норме латентность не страдает.

### 8.3. Защита от split-brain

- **Один писатель на деньги.** Billing активен только в одном регионе. Кворум etcd не даёт поднять второй primary.
- **Fencing.** Patroni с `pg_rewind` и отключением старого primary; без кворума запись не принимается.
- **Идемпотентность.** Даже при ошибке `unique(account_id, idempotency_key)` не даст списать дважды, расхождение поймает сверка.
- **GSLB.** Переключение по health-check, DNS TTL — лишь страховка.

### 8.4. Учения

Раз в квартал: имитируем отказ региона A, переключаем трафик/БД/MM2, замеряем фактические RPO/RTO, проверяем целостность `spend` и сверку (≤ 0,1%), фиксируем результат. Не уложились — считаем дефектом.

## 9. Что не взяли

| Вариант | Почему |
|---|---|
| Шардировать PostgreSQL по диапазону дат | Горячая партиция «сегодня», перекос |
| Шардировать Billing по `advertiser_id` сразу | Ломает глобальные сверки/инварианты; крайняя мера |
| Read replicas PostgreSQL для аналитики | Не решают построчный скан |
| Синхронная репликация для Redis | WAN убивает hot path |
| Мультимастер PostgreSQL | Split-brain/конфликты, для денег плохо |
| Авто-шардирование по CPU | Риск перекоса и backfill в пик |
| Один Redis Cluster на всё | Шумный сосед |
| Денормализация «на всякий случай» | Усложняет запись/миграции без подтверждённой выгоды |
